# t5 · 播放解析链埋点与基线测量

日期：2026-09-21 · 类型：测量（wayfinder task） · 关联：#329（本票）、#327（路线地图）、#335（下游决策票）、ADR-0014、`docs/wayfinder/2026-09-14-t3-tier3-mechanism-audit.md`

> **口径**：本报告回答「点歌到 URL 就绪」各环节花了多久、败在哪一环。
> **未覆盖最后一跳**（URL 就绪 → 真正出声，即播放器加载 + 解码），见 §5。
> **脱敏**：tier3 源一律记作 S1–S7（按用户本地清单顺序编号），端点、订阅地址、id 不入库。

## 0. 一页结论

1. **冷启点歌的真实分布是「两极」**：直连成功 ~70–110ms（23%）、tier3 兜底 2.4–5.4s（50%）、**6.1s 后失败（27%）**。总时延 P50 **3120ms** / P90 **6145ms**。
2. **预取命中确实是 0 等待**（实测 0.00–0.04ms，0 次 HTTP），**但只覆盖 23% 的歌**——探测腿按设计只做直连（`resolvePlayableSongDirect`，无 tier3），因此**永远暖不到那 50% 需要 tier3 的歌**。预取的收益上限被结构锁死在直连成功率上。
3. **tier3 腿是时延主体**，且坏源会吃满 6s 整链预算把好源饿死。受控实验（同一首歌、同一网络、只改源顺序）：
   - 真实清单顺序 → **6077ms，拿不到 URL**（第二首 6105ms 同样失败）；
   - 把能命中的源提到前面 → **1057ms，拿到 URL**（第二首 1186ms）；
   - 不放预算让整链跑完 → **32742ms** 才拿到第一个可用 URL。
4. **`tier3Stats` 会虚报命中**：被预算截断丢弃的命中照样 `hits++`。实测会话末 S3 `hits=17`，而同一批 QQ 歌 21/21 全部以 6.1s 超时失败——设置页显示「命中」而用户实际 100% 失败。
5. **ADR-0014 的「单源 2s 硬墙」是默认值，不是上限**：用户清单里显式 `timeoutMs: 15000/20000` 直接覆盖它。对**存量清单**，决策 2 的约束力为零。隔离实测单源真实成本：S1 11.0s、S2 20.7s、S7 22.3s。
6. **「隔日重播要重试/放不出来」是必然，不是偶发**：桌面预取是内存 30min（重启即空）；移动端有 12h 磁盘 URL 缓存，但写入时刻表 `urlWrittenAt` 是内存 Map（`cacheService.ts:33-36`），重启即丢 → 年龄未知 → 播放前强制探活 ≤1.5s → 签名已死 → 重新解析。签名寿命口径 ~15–30min（同文件注释），既有真机复现「《恋人》隔 3 小时重播必失败」。
7. **埋点形态建议**：**core 出结构化 trace、宿主落 sink**；常驻内存环形缓冲（会话内、不落盘、不外传），设置页诊断区可见 + 手动导出。实测开销 `performance.now()` 32ns + 记录对象 72ns，相对 P50 3120ms 可忽略。

## 1. 方法与样本

| 项 | 内容 |
| --- | --- |
| 环境 | Linux 桌面（WSL2），Node v24.10.0，真实公网 |
| 被测代码 | 仓库 `packages/core`（`npm run core:build` 后从 `dist` 加载，与移动端同入口） |
| 配置 | **用户真实配置**：`sourceModes` 七源全 `direct`；tier3 启用，1 条订阅、7 个源（S1–S7）；真实 kugou cookie |
| 样本 | 用户 `playHistory` 去重后 53 首中分层抽 22 首（netease 6 / qq 6 / soda 5 / kugou 3 / kuwo 2） |
| 方法 | 一次性 Node 探针（**未入库、未改仓库代码**）：在 transport 接缝记录每次原始 HTTP 尝试，在直连客户端与 tier3 resolver 接缝记录每段耗时，逐歌打点 |
| 说明 | 探针只挂在 core 的既有接缝上，不修改 core 源码；`packages/core/dist` 由当次源码构建 |

**流程定义**

- **Flow C（冷启，= 隔日重播的真实路径）**：清空预取缓存 → 直接 `resolvePlayableSongRouted`，`direct` 模式（用户真实配置）。历史/收藏/队列下一首走的就是这条。
- **Flow B（冷启，auto）**：同上但七源 `auto`。实测与 C 无差异——因为本样本里 tier3 是被「直连返回空串（无版权/VIP）」触发的，而 `direct` 模式**在空串分支同样进 tier3**（`sourceRouter.ts:539-542`）；`direct` 只拦「直连抛错」分支。
- **Flow A（搜索结果路径）**：先 `probeSongsBatch`（探测 + 写预取）再播放。
- **Flow P / R / S**：预取命中、同歌重复性、单源隔离，见 §2.4–2.6。

## 2. 基线数据

### 2.1 命中层级分布（22 首）

| 路径 | 预取命中 | 直连 | tier3 | 失败 |
| --- | --- | --- | --- | --- |
| Flow C 冷启（用户真实配置） | — | **5（23%）** | **11（50%）** | **6（27%）** |
| Flow A 探测→播放 | **5（23%）** | 0 | **11（50%）** | **6（27%）** |

- Flow A 的预取命中集合 **= Flow C 的直连成功集合**（同为 5 首）。原因：探测腿走 `resolvePlayableSongDirect`（直连-only，无 tier3），只有直连能解析的歌才会被写进预取缓存。
- 5 首预取命中里 **1 首是试听版（nonFull）**，播放时仍要进 tier3 尝试完整版（实测该首 6001ms）。**真正 0 等待的只有 4/22 = 18%。**
- 6 首失败**全部是 QQ**：直连返回空串（无版权/VIP）→ tier3 → 预算耗尽 → 空 URL。QQ 子样本 6/6 冷启不可播。

### 2.2 时延分解（ms）

| 段 | n | P50 | P90 | P95 | max | mean |
| --- | --- | --- | --- | --- | --- | --- |
| **总（冷启，Flow C）** | 22 | **3120** | **6145** | **6155** | 6160 | 2961 |
| 直连成功子集 | 5 | 72 | 108 | 108 | 108 | 78 |
| tier3 子集 | 11 | 2406 | 3340 | 5385 | 5385 | 2539 |
| 失败子集 | 6 | 6145 | 6160 | 6160 | 6160 | 6139 |
| 预取命中（Flow P，合成） | 5 | **0.00** | 0.04 | 0.04 | 0.04 | 0.01 |
| 直连客户端调用（全部方法） | 25 | 93 | 839 | 877 | 936 | 227 |

- 失败子集全部 ≈ **6145ms**，即 `TIER3_BUDGET_MS = 6000`（`sourceRouter.ts:314`）+ 直连解析开销。**6s 预算是失败路径的主导项，而不是网络本身。**
- 直连客户端里最慢的是汽水 `resolveUrlInfo`（P50 839ms）；netease/qq/kugou/kuwo 都在 15–160ms。
- 单次 HTTP 最大耗时 **12996ms**（S1 的一个 200 响应），说明「源站慢」真实存在，且当前**没有任何机制**把它限制在 2s。
- Flow B（auto）与 Flow C 数值几乎一致（总 P50 3007 / P90 6142），佐证本样本里 `auto|direct` 不改变链路。

**Flow R 同歌重复性（冷启 × 3 轮）**——不是随机抖动，是**按源确定**：

| 歌（源） | 第 1 轮 | 第 2 轮 | 第 3 轮 |
| --- | --- | --- | --- |
| kugou | 1815ms | 1773ms | 1637ms |
| kuwo | 106ms | 68ms | 68ms |
| netease | 69ms | 45ms | 42ms |
| **qq** | **6121ms / 失败** | **6142ms / 失败** | **6138ms / 失败** |
| soda | 5387ms | 2579ms | 4254ms |

### 2.3 失败原因分类（22 首）

| 类别 | 数量 | 说明 |
| --- | --- | --- |
| 空 URL 且 tier3 未在预算内交付 | **6（27%）** | 全部 QQ；等待恒为 ~6.1s |
| 直连抛错 | 0 | 本轮未出现 |
| 试听版（nonFull） | 1（5%） | 预取命中即试听版 |
| 无版权/空 URL 但 tier3 救回 | 11（50%） | 计入成功 |

**HTTP 尝试层分类（全部 flow 汇总，353 次尝试）**：`200 × 213`、`206 × 67`、`ECONNRESET × 73`。

- `ECONNRESET` 全部来自 S2（单源隔离里 4 次尝试 × ~5.0s = 20.7s）与 S7（4 × 4.3–7.6s = 22.3s）。
- **重试放大**：`transport` 的 `maxRetries=3` 使一次失败的逻辑请求变成 **4 次网络尝试**。S2 的「一次失败」真实成本是 20.7s。

### 2.4 tier3 每源（隔离测量，绕开 6s 预算取真实成本）

每个源单独成订阅，对匹配源的一首歌解析（QQ 歌用 QQ 歌，netease 源用 netease 歌，未声明源用 QQ 歌）：

| 源 | kind | 声明 source | timeoutMs | 目标源 | **耗时** | 结果 | HTTP 尝试 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| S1 | url-resolver | qq | 15000 | qq | **11002ms** | 未命中（200 但无可用 URL） | 1 |
| S2 | url-resolver | qq | 15000 | qq | **20714ms** | 失败（TLS/连接被重置） | 4 |
| S3 | url-resolver | qq | 15000 | qq | **987ms** | **命中** | 2 |
| S4 | url-resolver | netease | 15000 | netease | **973ms** | **命中** | 2 |
| S5 | search-then-resolve | （未声明） | 15000 | qq | **2617ms** | **命中** | 3 |
| S6 | url-resolver | kuwo | 15000 | kuwo | **156ms** | 未命中 | 1 |
| S7 | search-then-resolve | （未声明） | 20000 | qq | **22271ms** | 失败 | 4 |

**清单顺序即尝试顺序：S1 → S2 → S3 → S4 → S5 → S6 → S7。**

对一首 QQ 歌，可用源是 S1、S2、S3、S5、S7。其中 **S3（0.99s）与 S5（2.6s）都能命中**，但它们排在两个坏源之后：

- S1 单源 11.0s **已超过 6s 整链预算** → S3 一次都不会被请求；
- 即便 S1 侥幸快，S2 的 20.7s（重试放大）同样吃光预算。

**结论：清单里存在两个可用的 QQ 解析源，被两个坏源在前饿死——「多配源」在当前调度下确实是负收益，且这个现象在 ADR-0014 一期落地后依然成立**（见 §2.5）。

### 2.5 受控实验：只改顺序，同一首歌（决定性证据）

同一首歌《未完路线》(qq)、同一网络、同一清单，仅改变源子集/顺序：

| 实验 | 订阅（按序） | 预算 | 结果 | 耗时 |
| --- | --- | --- | --- | --- |
| A 对照 | [S3] | 有 | **命中** | **1251ms** |
| B 真实顺序 | [S1,S2,S3,S4,S5,S6,S7] | 有（6s） | **空 URL（失败）** | **6077ms** |
| C 真实顺序·不放预算 | [S1,S2,S3] | 无 | 命中 | **32742ms** |
| D 好源前置 | [S3,S5,S1,S2] | 有（6s） | **命中** | **1057ms** |
| E 真实顺序（第二首） | 同 B | 有 | **空 URL** | **6105ms** |
| F 好源前置（第二首） | 同 D | 有 | **命中** | **1186ms** |

C 的时间线（相对起点）：`0` 开始 → `12.7s` S1 未命中 → `33.4s` S2 失败 → **`35.5s` S3 命中**。
即：**真实链完整跑完需要 32.7s 才拿到第一个可用 URL**；6s 预算把它截成「6.1s + 空」。

> 口径提醒：预算截断**不取消**底层请求（`sourceRouter.ts:358` 注释、ADR-0014 已记录），所以 C 的时间线里混有 B 遗留请求的迟到日志；这不影响 A/B/D/E/F 的对比。

**可动杠杆（数据支持，取舍留给 #335）**：

1. **给单源超时封顶**（`min(source.timeoutMs, 2000)`）——S1 2s + S2 2s + S3 1s ≈ 5s < 6s，可救回 QQ；
2. **好源前置 / 按历史健康度排序**——同数据下 6077ms→1057ms；
3. **预算按源分配**（deadline 分摊，而非先到先吃满）；
4. 关掉/移除坏源（但这是用户自配清单，与 ADR-0014 决策 7「不做合规白名单」的精神一致）。

### 2.6 URL 生命周期与「签名过期」复现

**机制（代码事实）**

| 端 | 持久化 URL 缓存 | 重启后行为 |
| --- | --- | --- |
| 桌面 | **无**。预取缓存是内存 `Map`，TTL 30min（`prefetchCache.ts:21-23`）；队列/收藏/历史里的 `song.url` 实测为空串 | 冷启即空 → 全链重解析；#328 的 `warmupRestoredSong` 只为「恢复的当前歌」后台预热一次 |
| 移动端 | **有**。`songResourcesCache` 12h TTL，L1 内存 + L2 文件（`cacheService.ts`） | 写入时刻表 `urlWrittenAt` 是**内存 Map**，重启即丢 → `urlAgeMs()` 返回 `null` → `age == null` 触发**播放前探活** `isUrlAlive`（≤1.5s）→ 签名已死则删缓存重解析（`audioPlayer.ts:332-345`） |

**签名证据（本轮实测取到的 URL）**

- netease 直连 URL 形如 `https://m801.music.126.net/20260921203058/...`——路径里嵌**签发时间戳**，query 带 `vuutv`/`cdntag` 签名参数。
- QQ（经 tier3）URL 形如 `https://isure6.stream.qqmusic.qq.com/C600....m4a?guid=...&vkey=...&uin=...`——`vkey` 是时效签名。
- kuwo 直连为 `http://kw-*.kuwo.cn/<hash>`，无显式签名参数。

**本轮可测到的存活窗口**：对全部 32 个真实解析 URL 在 **+30~40 分钟**后逐一 Range 探活，**32/32 存活**（`206` + 1KB）。即「30min 预取 TTL」相对观测寿命是保守的。

**「隔日」的定性（数据 + 机制，非猜测）**：隔日首次播放**必然重新解析**，因为

1. 桌面根本没有持久 URL；移动端 12h 缓存即便未过期，年龄未知也会先探活（≤1.5s）而签名已死（寿命口径 15–30min，既有真机复现「隔 3 小时必失败」）；
2. 重新解析就是 §2.2 的冷启分布：P50 3120ms、**27% 直接失败**，QQ 子样本 6/6 失败。

所以用户报告的「要重试或直接无法播放」= **必然慢 + 相当比例必然失败**，两个原因都在我们自己的机制里，不是「源站偶尔抽风」。

### 2.7 「URL 校验」在哪一段

`resolvePlayableSongRouted` **自身不做任何 URL 校验**——它只解析出 URL。校验发生在两处旁路：

1. **探测腿**（`probeSongsBatch` → `resolvePlayableSongDirect` → `probeAudioUrl`）：搜索结果场景；22 首一批 5 首并发，实测整批 3872ms。它的产物就是预取缓存 + `audioTag`。
2. **移动端播放前探活**（`isUrlAlive`，≤1.5s，仅当缓存年龄未知/高龄）。

即：**「URL 校验」的耗时不在播放解析链里，而在探测/探活旁路**。埋点必须把这两段单独记，否则会把校验成本错记到解析腿上。

### 2.8 现有 `tier3Stats` 够不够

现状字段（`tier3Api.ts:109-115`）：`hits / misses / skipped / searches / lastError`。

| 缺口 | 证据 | 需要的字段 |
| --- | --- | --- |
| **hit 与 delivered 不分**（最严重） | 会话末 S3 `hits=17`，同期 QQ 歌 21/21 失败——命中被 6s 预算截断丢弃，统计照记 | `delivered`（真正返回给调用方的次数）；或 `hits` 只在 `Promise.race` 获胜时自增 |
| **没有耗时** | 设置页只能看次数，看不出「S1 要 11s」 | 每源 `ms` 分位（或 `lastMs` + 累计 `totalMs`） |
| **失败原因只有「最近一条」** | `lastError` 单值、非累计 | `lastErrorClass`（timeout / tls / http4xx / http5xx / empty）+ 分类计数 |
| **没有重试/尝试数** | S2 一次失败 = 4 次 HTTP | `attempts` |
| **没有「被预算丢弃」计数** | 上一条证据 | `discarded` |
| **`searches` 只覆盖搜索腿调用次数**，没有搜索腿的每源成败 | ADR-0014 决策 5 已补 `searches`，但搜索腿仍不进 per-source 命中/失败 | 搜索腿的 per-source `hits/misses` |

**结论**：不够用，且当前形态是**误导性**的（把「被丢弃的命中」记成「命中」，方向偏向「看起来源很好」）。

## 3. 埋点形态决策

### 3.1 写在哪一层：**core 出结构化 trace，宿主落 sink**

- **core 计算**（链路语义在这里，双端天然一致）：
  - `resolvePlayableSongRouted` 出入口 → `totalMs`、`layer`（`prefetch|direct|tier3|fail`）、`nonFull`、`prefetchHit`、`tier3Engaged`、`reason`（预取命中 / 直连空串 / 直连抛错 / 无效 / 试听版 / 预算超时）；
  - 直连腿 → `directMs`（方法名 + 源）；
  - `tryTier3` → `tier3Ms`、`timedOut`（预算 vs resolver 结束）；
  - tier3 源循环 → **每源一条** `{sourceId, ms, outcome: hit|miss|error|skipped|discarded, errorClass}`；
  - `probeSongsBatch` → `{songId, resolveMs, validateMs, tag}`（§2.7 的校验段）。
- **宿主落 sink**：`setPlaybackTraceSink(sink | null)`，与既有接缝同构（`setSourceModePersister` / `setTier3Persister` / `setCookiePersister` / `setTier3Deps`）。桌面主进程、移动端 service 各自注册；core 内**零 I/O**的规则不破。
- 不采用「只在宿主量」：宿主只能测到总时长，拆不出「预取命中 / 直连 / tier3」三段，也拿不到每源成败——正是本票要回答的问题。

### 3.2 常驻与否：**常驻、内存、会话内、不落盘**

- 常驻：隔日/真机样本需要跨多次真实播放采集，debug 开关采不到；且本轮已证明「偶发」其实是**必然**，抽样必须覆盖真实使用。
- 内存环形缓冲（建议 200 条）+ 会话内：与 `tier3Stats`（ADR-0014 决策 5「仅会话内、不持久化」）同一取向；也避免「昨日状态污染今日判断」。
- **不落盘、不外传**：本应用无账号、无遥测；落盘只在用户点「导出诊断」时发生（写用户选定的文件）。
- 失效安全：未注册 sink = 零成本直接返回（§3.4）。

### 3.3 用户能否看到：**诊断区可见 + 手动导出，不打扰播放**

- 移动端**已经有**用户可见的耗时日志（`useLogsStore`）：`[耗时] 播放准备开始` / `直链就绪: 解析耗时 Xms` / `缓存直链已失效（探活 Xms）` / `播放器就绪(出声): 总耗时 Xms`（`audioPlayer.ts:127/302/341/374`）。这套日志**只在移动端**，桌面**没有对应物**（`src/` 里没有 logs store）。
- 建议：把上面这 4 个**字符串日志升级为结构化 trace**（同一份数据既喂日志又喂统计），桌面补齐同等能力；设置页在既有「每源解析统计」旁加一个**播放诊断**区：最近 N 次解析的 `layer / totalMs / 各段 ms / 失败原因`，加「导出」。
- 播放中**不加**任何新 UI/提示（失败文案分级是 #335 决策 4，不在本票）。

### 3.4 开销（实测）

微基准（1e6 次，Node 24）：

| 操作 | 单次 |
| --- | --- |
| `performance.now()` | **32ns** |
| 构造一条 trace 记录对象 | **72ns** |
| 环形缓冲 push（容量 200） | **48ns** |

即一条 trace ≈ **150ns**，相对冷启 P50 3120ms 是 **0.000005%**；即使对 70ms 的直连成功路径也是 0.0002%。**「不得引入可感知开销」满足**——但实现时必须遵守：sink 为空时**不构造记录**（只读 `performance.now()` 也不做），且**不在热路径做字符串拼接**（现移动端日志的模板字符串才是真正要收敛的开销）。
