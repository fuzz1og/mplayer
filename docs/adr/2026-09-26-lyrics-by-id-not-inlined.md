# 歌词按 ID 直取：列表不再内联歌词

日期：2026-09-26 · 状态：已接受 · 关联：**#409**（本决策票）、#408（出网治理）、#412（桌面杂项，下载侧 .lrc 缺口）·
依据：2026-09-26 架构与性能静态评审（纯静态、未发上游请求）；取代 ADR `2026-09-23-tier3-failure-attribution.md` 之前 #242 确立的「网易歌词内聚进内容能力」形态

## 背景

#242 让网易内容能力在**每个内容方法返回前**对列表中每一首歌各发一次取词请求（`fillLyrics`，
并发 8、单次调用预算 10s），把整段 LRC 内联进 `Song.lrc`。这个循环**不在任何闸门之内**——
不属 tier3 解析腿，也不经 transport 的任何并发约束。放大链（静态推导）：

| 入口 | 列表规模 | 取词请求数 |
|---|---|---|
| `getToplists`（发现页首屏） | `n: 100000` 取榜单全量 tracks | **~300**（热歌榜 200 + 新歌榜 100，估算） |
| `getRecommendedSongs(100)`（推荐页） | 100 首池 | **~100** |
| `getPlaylistSongs(id, 0, 0)`（链接导入） | 全量，可达 1000 | **~1000** |

而消费侧只用得到 `name / artist / cover`：`discoverStore` 拿 200 首后 `.slice(0, 10)`，
推荐页只展示 5 首——请求数与展示量差 30 倍。桌面端还多付一次代价：内联的 LRC 全文随
IPC 单通道回传（`musicApiHandlers` 原样回传），整歌单 payload 可达 MB 级。

## 决策

1. **内容方法只返回轻量 DTO。** 网易内容方法不再内联歌词，列表结果里的 `Song.lrc` **恒为空**。
   `getPlaylistSongs` 的「点开即播」批量 URL 腿保留（1 请求 / 1000 id，与列表规模无关）。
2. **歌词改为播放期按源内 ID 直取。** 网易与汽水同档，都是「按 ID 直取歌词源」：
   core 出 `getNeteaseLyrics(songId)`（`api/neteaseDirect`），经 `musicApi` 门面暴露给双端；
   缓存 key `lyric_id_<songId>`、TTL 1 天、**命中零请求、空词也缓存**（值包 `{v}` 区分
   「无缓存」与「确认无词」）、**失败不缓存**且返回空串不上抛（歌词拿不到不该让播放失败）。
   语义与原地批量实现逐条一致，只把**调用时机**从「列表返回前」改成「播放期按需」。
3. **双端共用 core `shared/songLyrics` 的决策，不各写一份。** `songUsesSongidLyrics` 覆盖
   `netease | soda`；`isInlineLyrics` **保留**，但语义收窄为「存量持久化数据兼容守卫」——
   #409 之前写入收藏/历史/本地歌单的网易条目里可能仍是内联 LRC 文本，消费端必须先问它。
4. **堵住从播放路径漏回来的请求。** `fetchLrcInBackground` 对「按 ID 直取歌词源」只处理封面；
   **封面已在且未要求刷新时直接返回**。这是本决策的必要组成：列表 `lrc` 变空后，原来的
   `!force && song.lrc` 早退不再成立，若不改，每播一首网易歌都会多打一次搜索请求——
   正好把本决策省下的请求从另一条路打回来。

## 备选与否决

- **保留内联，只加预算与去重**：否决。它只能「少打一点」，删除才能「不打」；而且内联文本随
  IPC 回传造成的 MB 级 payload 只有删除才消得掉。
- **让桌面与移动端各自实现按需取词**：否决。两端歌词决策已经漂移过一次，`shared/songLyrics`
  就是那次收敛的产物（#242 的教训）；再分叉必然二次漂移。
- **保留网易的搜索补词兜底**：否决。按 songId 直取是权威答案，搜索拿不到更好的结果，
  只会多一次请求。
- **把汽水也统一成取词 URL 形态**：否决。汽水直连搜索恒不带 `lrc`（`searchSongsSoda` 恒空），
  分享页才是唯一免登录通路。
- **顺手收口 `musicApi.ts` 的 3 处 `axios` 绕过点**：不在本决策范围。那属行为变更
  （引入重试与代理语义），已在 #408 的 ADR 治理边界里登记。

## 后果

- **跨端数据契约变更**：`Song.lrc` 在列表结果里**不再可信**（恒空）。任何消费端不得再假设
  列表结果带词；存量数据的内联文本由 `isInlineLyrics` 兜住。
- **请求量**：发现页冷启 ~300 → **0**；推荐页 ~100 → **0**；网易歌单全量 N → **0**。
  播放一首网易歌新增 **1** 次取词请求（按需），重复播放由 `lyric_id_<id>` 缓存兜住。
- **歌词首行延迟**：从「列表加载时已就绪」变为「播放时一次 RTT」。由 PlayerOverlay 的
  `lyricsLoading` 与桌面 `lyricsLoading` 覆盖，**不阻塞出声**（歌词获取本就是 fire-and-forget）。
- **桌面 IPC payload 不再含 LRC 全文**，整歌单回传从 MB 级降回 KB 级。
- **下载侧 `.lrc` 仍按 `song.lrc`（URL）驱动**：网易/汽水恒空故不生成侧车歌词——这是既有缺口
  （记录在 #412），本决策未改变，也不假装已解决。
- **测试面**：`neteaseContent.test.ts` 从「断言内联」改为「断言**零取词请求** + 按需缓存语义」；
  双端各补一条「按 ID 直取、不触发搜索」的断言（含桌面 `getNeteaseLyrics` 与移动端
  `fetchLrcInBackground` 对网易只处理封面）。
