# 0012 · 歌曲身份与可播资源值（跨端单一语义）

日期：2026-09-10 · 状态：已接受 · 关联：#307（架构评审候选 06）· 实现：待 PR

## 背景

「一首歌」在仓库里有两种 id 形态：直连搜索产出裸数字（`123`），单曲换源后写成 `${sourceType}:${rawId}`（`kuwo:456`，旧数据可能多层嵌套 `kuwo:kugou:123`）。而缓存键、可播性徽标与收藏去重直接拿 `Song.id` 当唯一键：

- `songResourcesCache` 的不变量写死「songId 已含源前缀，跨源唯一」（`cache/songResourcesCache.ts:36-39`），但直连搜索不满足它（`api/neteaseDirect.ts:96,521`）→ `song:123` 会被两个源的歌共享，串直链、串封面、误删条目；
- 桌面可播性徽标按裸 id 存在搜索页 store（`store/searchStore.ts:82-99`），移动端按 `sourceType:id` 独立 store（`mobile/stores/audioTagStore.ts:7-22`）——两端两种键，桌面跨页播放时写入静默失效；
- 「缓存 → 严格匹配搜索 → 回写 DB」编排在桌面复制 5 份，热榜那份漏了精确匹配守卫（`pages/HotlistDetailPage.tsx:58-64`），会播同名不同歌手的歌；
- 两端外层缓存都把 core 已返回的 `{ url, nonFull }` 收窄成 `string`（`store/playerStore.ts:158`、`mobile/services/cacheService.ts:33-45`）→ 预取命中的试听版被回写 `valid`，丢掉换源提示；
- core 自己的预取缓存反而是正确形状（`api/prefetchCache.ts:27-29` `${sourceType}:${id}`）——同一概念两套键。

`Song.id` 是收藏/历史/歌单成员的持久化主键，直接规范化它需要数据迁移与回滚方案，收益与派生键等价。

## 决策

1. **身份派生，字段不动**：core 提供唯一的歌曲身份推导 = 音乐源 + 去源前缀的真实 ID（多层嵌套前缀按最外层源折叠，`kuwo:kugou:123` → `kuwo:123`）。`Song.id` 字段与持久化存量不因它改变；缓存键、可播性标记、去重一律走派生身份。旧键不迁移，靠各自 TTL 自净。
2. **可播资源是一个值，不是 string**：播放资源值 = `{ url, nonFull, ts }`（直链、是否试听/不完整、写入时间）。`cover`/`lrc` 仍由 `songResourcesCache` 三件套承担各自 TTL，不并入。
3. **编排收敛 core，依赖注入**：core 提供「取缓存 → 旧签名死链判定 → 精确匹配搜索 → 写缓存」的纯编排；桌面（IPC 缓存/DB）与移动（进程内）各是一个薄适配器，把读缓存、写缓存与写回端口注入。精确匹配守卫、nonFull 保留、失败不改写有效旧值等规则只存在于编排内。
4. **可播性标记独立成读模型**：不再寄生搜索结果 store；按身份键索引，播放侧只写、任意列表按需订阅（移动端 `audioTagStore` 形状推广到桌面）。

## 后果

- 跨源同 id 不再串缓存/串封面；试听版命中预取仍带 `nonFull`，换源提示不丢；
- 身份/键/TTL/守卫/写回规则单点，桌面 6 份编排收敛；新列表接可播性标记零成本；
- 旧缓存键（裸 id）在 TTL 内自然淘汰，无需迁移脚本；
- 代价：身份推导多一层函数调用；两端外层缓存改存值结构（一次性）。

## 回退选项

不采用：全面规范化 `Song.id`（动持久化主键，需迁移与回滚）；只就地拼 `sourceType:id` 不建 core 模块（规则继续散落，正是本缺陷的成因）；把 `cover`/`lrc` 并入同一值（两种 TTL 与死链判定揉在一起，语义层变胖）。
