# 移动端封面加载：窗口化 + 失败重试（不设闸门）

- 日期：2026-09-30 · 状态：已接受（同日修订） · 关联：**#496**（本决策票）、#417（歌手页专辑面）、#406（专辑页 UI）
- 依据：ADR `2026-09-26-outbound-request-governance.md`（决策 5：图片不过 core 闸门）、ADR `2026-09-29-queue-virtualized-sortable-list.md`（同一「挂载副作用」口径）
- **同日修订说明**：本 ADR 初版（文件名 `2026-09-30-mobile-cover-load-gate.md`）提出「移动端封面在飞闸门
  （`services/coverLoadGate`，在飞 6 + FIFO + 20s 槽位墙钟）」。当天在雷电模拟器上实测后**撤销该决策**，
  闸门与其单测一并删除，文件随之更名。

## 背景

1. 决策 5 把**图片**排除在 core 出网闸门之外（「两端都是原生 `Image` 直连 CDN，不过 core」）——
   当时是如实记录，不是没有代价。
2. #417 把移动端歌手页的专辑分区从 20 张提到 **100 张**，而横滑条当时是**普通 `ScrollView`**：
   一进歌手页 = 100 个 `<Image>` 同时挂载。
3. 同票新增的专辑时间线页 `PAGE_SIZE = 100` 且**没接** `listWindowProps`（RN 默认 `windowSize: 21`），
   3 列网格同样整页铺开。
4. 原 issue（#496）报的现象：上游限流 → 连**已经发出**的图也卡住拿不到。

## 决策

1. **窗口化（保留）**：歌手页横滑条改**横向 FlatList**（窗口 3 屏、首批 4、每批 4）；
   专辑时间线页 `PAGE_SIZE` 100→30 并接 `listWindowProps`（窗口 7 屏、每批 8）。
   「数据页大小」与「渲染窗口」分开看。
2. **不设封面在飞闸门（撤销同日提案）**：删除 `packages/mobile/services/coverLoadGate.ts`。
   闸门的前提是「先拿槽位再挂图、`onLoad`/`onError` 回来释放」；实测这个前提在 Android 上不成立：
   - 被 `removeClippedSubviews`（Android 默认 true）裁掉的离屏 cell，原生视图被 detach，
     它的 `<Image>` **既不 `onLoad` 也不 `onError`**（实测：一次进页 21 次挂图只有 3 次回调）；
   - 本机还有一批图片请求**长时间不回调也不失败**（同一批 URL 宿主 `curl` 是 200）。
   两者都让槽位被占到 20s 墙钟才归还；队列一长，**真正可见的封面排在后面被饿死**——
   实测「发现页 → 歌手分类 → 歌手页 → 专辑时间线」整页灰，且会连累发现页/推荐页。
3. **失败重试一次（`COVER_RETRY_DELAY_MS` = 1.2s）**：`components/LazyCover.tsx` 在 `onError` 后换 `key`
   重新挂载一次（强制重发请求），仍失败才回调 `onError`（埋点入口不变）。
   这一条与闸门无关，是独立的既有缺口：失败封面此前只记一行日志，那块就永久灰。
4. **封面渲染仍统一走 `LazyCover`**：`uri` 为空渲染同 style 的空 `View`（与「图还没到」同形，不二次跳动）
   + 失败重试 + 埋点单点。首屏关键封面（折叠 Hero / 迷你播放栏 / 全屏播放器）不经过它。
5. **并发交给窗口化与图片栈自身**：Fresco/OkHttp 本就有连接与并发上限；不再叠一层全局串行点。
6. **封面按各源 CDN 的机制要缩略图，规则放 core 一处**（`shared/coverUrl.ts`：`COVER_SIZE` + `coverThumbUrl`，
   两端共用）。**各源机制不一样**，不能一刀切加查询参数：
   - **网易** `p*.music.126.net`：查询参数 `?param=WxH`。实测同一张专辑封面原图 **272 KB** →
     1080y1080 94 KB / 640 41 KB / 320 14.5 KB / 200 **7 KB** / 120 **3.3 KB**。
   - **QQ** `y.gtimg.cn`：**路径模板**里的 `R300x300`（core 生成 URL 时就是它）→ 改成 `R{size}x{size}`，
     但档位是**白名单**：实测只有 120 / 150 / 180 / 300 / 500 / 800 返回 200，200 / 320 / 1080 恒 404
     （8 个专辑 mid 结果一致）→ 请求前吸附到「不超过请求值的最大档」。v1.8.6 桌面端行封面默认 icon 档 200，
     正好落在 404 上，QQ 行封面全灰，已由 #537 修复。
   - **酷狗** `imge.kugou.com`：URL 里带 `{size}` 占位符，映射时已替换成 300（见 `kugouDirect`）→ 已经够小。
   - **酷我 / 咪咕 / 千千 / 汽水**：机制**未验证** → 原样返回。**未命中白名单一律不动**：
     有些源带签名 / 防盗链（汽水的 `douyinpic`），乱加参数会 403 —— 安全默认是「不省」。
   - CDN 不支持 webp/avif 协商（带 `Accept: image/webp` 仍返回 `image/jpg`），所以**尺寸参数是唯一的字节杠杆**；
     `Cache-Control: max-age=31536000`，重复加载本来就零成本。
   - 取图点：移动端 `LazyCover`（row/icon/thumb 档）+ 三个不过闸的裸图点（Hero / 全屏播放器 / 迷你播放栏）；
     桌面端 `<img>` 一并在同一份 helper 上接线（见「后果」）。

## 备选与否决

- **在飞闸门（初版决策，已撤销）**：见决策 2 的实测反例。教训一句话：
  **一个全局资源如果只在「回调回来」时释放，就不能放在回调可能永远不来的路径上。**
- **显式关掉 `removeClippedSubviews`（让离屏图也回调）**：实测**更糟**——窗口内所有离屏 cell 都开始真的
  发请求，一起挤那 6 个槽位，可见封面被彻底堵死（发现页/推荐页一起变灰）。离屏不该加载，这正是裁剪的用途。
- **每个列表自己做可见窗口（`LazyCover.active` + 各列表 `viewabilityConfig`）**：否决。闸门是全局的，
  把「谁有资格拿槽位」拆成「每个调用点记得接」的约定式接线，漏一个列表（实测：发现页歌手网格）就复现饥饿；
  横切关注点必须只有一个落点。
- **把图片并进 core `transport` 的闸门**：否决。图片不过 core；要并进去就得自建图片管线
  （缓存/解码/内存全归我们），成本与收益不成比例。
- **换 `expo-image`**：本轮不做。它自带 `cachePolicy`/`priority`/`recyclingKey`/重试，是「手搓
  `LazyCover` + 闸门」的正统替代；先按本决策把复杂度降下来，等有明确收益（滚动内存、列表复用）再单独评估
  （含双端与主题适配成本）。
- **只把槽位墙钟从 20s 缩短**：随闸门一并撤销。

## 后果

- 并发回到「窗口内挂多少就发多少」：横向 rail 首批 4；时间线每页 30（窗口 7 屏）；歌曲列表窗口 7 屏。
  图片栈自身再限一层。**没有全局串行点，也没有饥饿。**
- 恢复原生出图节奏（不再有人为的「一张张排队」）。
- 失败封面重试一次，减少永久灰块；仍失败即真的取不到（`logCoverError` 埋点保留）。
- **未解决**：
  - 本机仍有 p1/p2 偶发失败（宿主 `curl` 200、App 内失败）——根因待单独排查（可能与 HTTP/2 连接复用或
    CDN 对设备侧 UA/UA-less 请求的处理有关）。
  - 内容元数据落盘：`ContentCache` 仍是**同步**接口（core 侧），移动端磁盘 L2（`CacheKernel`）接不上。
    已单独成票 **#498**，本票不碰。
