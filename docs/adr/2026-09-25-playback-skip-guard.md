# 播放失败的护栏语义：core 单一决策、固定跳歌上限、离线即停、坏歌记忆

日期：2026-09-25 · 状态：已接受 · 关联：**#385**（本决策票，spec 见其评论）、#389（直连 3s 墙，失败耗时上界）、#392（直连腿时长取证，失败判定的另一半）、#387（桌面等待态，失败前的可见性） · 依据：`docs/research/2026-09-23-playback-failure-ux-comparison.md`（六家开源播放器对标）

## 背景

断网或订阅源整体失效时，两端的跳歌护栏都有系统性缺陷（#385 D1–D6）：

1. 护栏用**队列长度**当阈值——200 首队列会依次试 200 首，且每首先走一轮 fresh 重试，
   最坏约 400 次链式尝试；UI 在闪歌名而全程无声。
2. 手动点歌把 `failureCount` 重置为 0——「断网中点歌 → 跳 3 首 → 再点」可无限循环。
3. 两端都没有网络态检测：断网与「这首歌恰好死了」被当成同一件事。
4. `audioTag: 'invalid'` 只驱动徽标，不参与跳歌决策；且仅会话内。
5. 双端两份实现、两套文案（`连续 N 首无法播放，已暂停` vs `可长按歌曲换源，或稍后再试`）。
6. 用户主动点的那首也会被静默跳走，且「失败即跳」被硬编码、不可关。

对标调研（lx-music / MusicFree / listen1 / YesPlayMusic / FeelUOwn / MPlayer）：MPlayer 是唯一
「没有绝对跳歌上限、没有坏歌记忆、没有网络态」的一家；「失败即跳」在 lx-music
（`autoSkipOnError` 默认 true）与 MusicFree（`autoStopWhenError` 默认 false）都是用户偏好。

## 决策

1. **护栏是 core 的一个纯函数 + 会话内状态，宿主只做接线。**
   新增 `packages/core/src/shared/skipGuard.ts`：`decideAfterPlaybackFailure(input)` 输入
   离线态 / 偏好 / 有无下一首 / 连续失败计数 / 是否本地，输出 `skip | stop` 与**一句话文案**；
   状态（连续计数、坏歌集合）为模块级、会话内、不落盘（与 `tier3Stats`/`prefetchCache` 同取向）。
   **文案是 core 单一来源**，宿主不得再写失败提示。
2. **连续失败用固定绝对值上限 `SKIP_LIMIT = 3`**，与队列长度无关。每首仍保留一次 fresh 重试
   （同曲换新 URL），因此最坏 = 3 首 × 2 条链。
3. **决策优先级（定序，不是调参）**：离线 → 停；关闭「失败即跳」→ 停；**无下一首 → 停**；
   连续失败达上限 → 停；本地文件 → 跳（文案不同）；否则 → 跳。
4. **离线判定由宿主注入 predicate，且必须在进解析链之前生效**：core 保持零 I/O；桌面用
   `navigator.onLine === false`，移动端用 `@react-native-community/netinfo`
   （`isConnected === false || isInternetReachable === false`）。判定为离线时**不发起解析**
   （省掉直连 3s 墙 + tier3 6s），直接停并提示；离线**不计入**连续失败、不写坏歌记忆。
5. **坏歌会话内记忆并参与选曲**：终局失败即记住（键 = core 歌曲身份键），跳歌时主动跳过
   （选曲同样下沉到 core `pickNextSongAfterFailure`，两端不再各写一份）。
6. **「失败即跳」是用户偏好，默认 `true`**（保持既有行为，对齐 lx-music）：双端设置页各一个开关
   （桌面「播放」区 / 移动端「播放」节），语义与文案同源。
7. **连续失败计数只在两处变化**：终局失败（fresh 之后仍失败）+1；**真正开始播放**归零。
   **手动点歌不清零**（修 D2 的无限循环）。
   - 桌面：`play()` 走到 `audioPlayer.load` 成功即视为「真正开始播放」（load 失败会抛）。
   - 移动端：归零点放在**播放器就绪（`isLoaded`）事件**——expo-audio 的加载错误是异步事件，
     `play()` 返回不代表能出声，若照抄桌面会把失败歌算成功、计数永远归零。
8. **两端同一门语言**：失败处置的入口、判定与文案都收敛；保留的端差异只有「何时算开始播放」
   （见决策 7）这一条，且它由运行时分派模型决定，不是语义分叉。

## 备选与否决

- **两端各自实现**（现状）：语义与文案已经漂移过一次，否决；#385 的验收要求「core 单一来源」。
- **保留队列长度相对阈值**：断网 200 首队列 = 200 次尝试，与「快速失败」直接冲突，否决。
- **计数在手动点歌时清零**：正是 D2 无限循环的成因，否决。
- **坏歌记忆持久化**：源临时抖动不应变成永久失效（沿用 ADR-0014 决策 4 的理由），否决。
- **自动熔断 / 自动换源**：跨源自动救回已由 #386 裁决不做；本决策只做「停或跳」。
- **在 core 里做网络探测**：core 零 I/O 是既有红线，离线判定必须以 predicate 注入，否决。

## 后果

- **断网/坏源的最坏尝试次数有了硬上界**：3 首 × 2 条链，且离线时 0 次——不再出现「翻完整张队列」。
- **文案收敛**：两端不再各写一套失败提示；改一次两端一致。
- **「失败即跳」可关**：用户在设置页可把决定权拿回（关闭后失败即停）。
- **移动端新增一个原生依赖**（netinfo）：需原生重建；Expo Go 不含该模块，`isOffline()`
  在拿不到 NetInfo 时按「在线」降级（不崩、不误报离线）。
- **残余风险（如实记录）**：
  - 优先级「离线最前」意味着**本地文件播不动 + 设备离线**时会报「离线」而非本地文案；
    这是刻意选择（离线是当下更可操作的归因），如需区分须在 core 调整优先级；
  - 桌面 `navigator.onLine` 只反映「明确离线」，在线但不可达仍要靠解析链上界兜住；
  - 连续计数的归零点依赖各端「开始播放」的判定（见决策 7），仍是端差异点，需在改动时留意。
