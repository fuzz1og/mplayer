# 出网治理：transport 双层在飞闸门与 AbortSignal 贯通

日期：2026-09-26 · 状态：已接受 · 关联：**#408**（本决策票）、#399（墙/预算口径统一）、#409（列表数据瘦身）·
依据：2026-09-26 架构与性能静态评审（桌面端 + 手机端，纯静态、未发上游请求）、ADR `2026-09-14-tier3-scheduling-and-source-ownership.md`、ADR `2026-09-25-tier3-source-scheduling.md` 决策 8

## 背景

`packages/core/src/api/transport.ts` 是双端**唯一**的出网接缝（23 个生产调用点，10 个源客户端 +
`musicApi` + 嗅探 + 时长取证），接缝上有可注入的实现（默认 axios + 测试假传输），但**没有任何纪律**：

1. **无并发上限。** 全仓唯一的在飞上限是 tier3 解析腿的 `MAX_TIER3_IN_FLIGHT = 3`
   （`shared/sourceRouter.ts:495`）——它约束的是「跨歌同时在解析的歌数」，**不是出网请求数**，
   且只覆盖 tier3 解析。直连腿、tier3 搜索腿、歌词腿、嗅探、时长取证全部无闸门。
2. **无取消。** `TransportRequest` 没有 `signal` 字段，axios 调用也未带 signal
   （`transport.ts:17-42` / `:214-228`）。3s 直连墙（`sourceRouter.ts:369-374` 的 `Promise.race`）
   与 6s tier3 预算**只放弃等待**——底层请求继续跑完并继续重试。这一点被两处注释明确记录：
   `sourceRouter.ts:357-358`「底层请求自然结束、结果丢弃」、`tier3Api.ts:220-221` 同款。
3. **重试放大且无退避语义。** `maxRetries = 3`（`transport.ts:123`）对**每一条**逻辑请求生效
   （5xx 与可重试网络错误），最坏 4 次真实 HTTP。429 既不重试也不读 `Retry-After`：
   限流被当成「这个源不行」→ 路由切到下一个源 → 制造新的请求。
4. **放大是真实存在的，不是理论值。** 手机端「冷启动 + 首次打开发现页」的上游请求量在**数百次**
   量级（推导见 #409）：网易内容能力在返回列表前对每一首歌各发一次取词请求，并发 8、窗口 10s，
   **完全在所有闸门之外**。闸门是这类「某个调用点自己放大」问题的最后一道防线。

已有先例可循：ADR `2026-09-25-tier3-source-scheduling.md` 决策 8 已经确立了本仓对并发的形态立场——
**FIFO 排队、排队期间各调用方自持预算、上限取「与既有下载并发同量级」的 3**，并明确拒绝「并行打多个上游」。
本决策把同一形态从 tier3 解析腿提升到整个出网层。

## 决策

1. **双层在飞闸门：全局 6 + 每 host 2，FIFO 排队。**
   全局上限必须**大于**任何单腿自己的上限（tier3 K=3 / 下载 3 / 搜索 3），否则单腿会被外层闸门自我饿死；
   取 6 = 两条腿各自跑满。每 host 上限取 2 的理由是「同一主机不要有两条以上在飞」能覆盖绝大多数风控形态，
   且留出实测调参空间。**同 host 的等待者严格 FIFO**；跨 host 允许越过被 host 容量挡住的队首，
   避免头阻塞。
2. **`TransportRequest` 增加可选 `signal`，并在排队与在飞两个阶段都响应 abort。**
   排队期间 abort → 从队列摘除并 reject；在飞期间 abort → signal 传给 axios。
   **被 abort 的请求绝不调用底层传输**（这是可断言的）。
3. **每一次真实尝试各占一个槽位**（重试是新的出网，重新取槽），槽位在底层传输 settle 后释放。
4. **429 / `Retry-After` 退避本轮不做。** 退避是**策略**（退避多久、哪些源需要），需要先有闸门产出的
   指标才谈得上；本轮只装机制。记为「已知未解决」。
5. **治理边界（显式排除）。** 以下出网路径**不受**本闸门约束，且这是有意为之：
   - 桌面端**音频拉流**：走渲染进程 Chromium 网络栈（见 ADR `2026-09-21-tier3-url-substitution.md`），
     与主进程 transport 不同进程，插不进去；
   - **下载服务**：两端各自已有独立并发门控（桌面 `DEFAULT_MAX_CONCURRENT`、手机端 expo-file-system）；
   - **图片**：两端都是原生 `Image` 直接拉 CDN，不过 core。
   写入本条的用途是让下一个读者不必再问「为什么图片不受管」。
6. **可观测性。** 暴露最小集合：当前在飞数、并发峰值、最长排队等待，落在**既有的设置页诊断板块**，
   不新增面板、不做独立页面（对齐 ADR `2026-09-25-tier3-source-scheduling.md` 决策 2 的口径）。
   计数只在诊断区被读，不进每次请求的热路径。

## 备选与否决

- **只做全局单层闸门**：否决。手机端的取词腿**全是同一个 host**，全局上限拦不住「同一台主机被 8 条压」。
- **每 host 加最小间隔（pacing）**：本轮否决，非永久否决。qq 的 `code=2001` 是**速率**墙不是并发墙
  （#388 实测：200ms 间隔 12 次挂 10 次，400ms 则 14/14 成功），并发上限**治不了它**；
  但 pacing 需要按源配参数与实测数据，先把参数做成同一模块里的可选位、留空，等指标到位再填。
- **用模块级 ambient scope 传 signal（而非显式可选字段）**：否决。它依赖调用链的同步前缀在
  `request()` 被调用时仍然成立，任何一处先 `await` 就静默失效——脆弱、且无法在接口上测试。
- **队列超限时立即失败**：否决。会把「慢」变成「错」，弱网下大面积误伤，且与 ADR 2026-09-25 决策 8
  已经确立的 FIFO 排队形态冲突。
- **让闸门自己管墙钟（transport 内部超时）**：否决。墙的语义属各腿（直连 3s / 单源按 kind / 嗅探 1s），
  transport 只该管「同时在飞多少」，管时间会让两套口径再次分叉——这正是 #399 要收拾的问题。

## 后果

- **接口向后兼容。** `signal` 是可选字段，23 个生产调用点零改动即可编译；
  但**取消要真正生效，仍需各腿把 signal 传下来**——本决策只把字段与语义放到接缝上。
- **排队会占用调用方墙钟的「等待」时间。** 调用方的 `Promise.race` 仍在墙点触发（UI 行为不变），
  但底层请求不再无限期占用上游连接。这是相对现状的净改善，不是回归。
- **上限是全局单点，弱网下排队等待可能变长。** 6 / 2 是**起步值**而非结论值，
  依赖第 6 条的可观测性来判定是否要调——这也是为什么指标与闸门同批落地。
- **ADR-0014 后果里挂着的「服务器忽略 Range 时的全量缓冲需响应字节上限/提前中断，依赖 transport 是否支持」
  仍未解决。** 本次不做，如实记录，不假装已解决。
- **分阶段落地**：
  - **第一阶段（#408 本票）**：闸门 + `signal` 字段 + 重试的 abort 感知 + 指标 + 测试。
  - **第二阶段（跟随票）**：7 个直连客户端的 capability 方法接可选 signal，
    `timedDirectCall` / `withSourceDeadline` 在墙点 `abort()`，把「放弃等待」变成「真的停掉」。
  - **第三阶段（待指标）**：429 / `Retry-After` 退避与每 host pacing。
