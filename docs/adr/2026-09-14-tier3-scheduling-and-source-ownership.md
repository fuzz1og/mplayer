# 0014 · tier3 调度、预算与源归属（并行、超时阶梯、赢家嗅探、显式 source）

日期：2026-09-14 · 状态：已接受；**决策 1 的「按源类型并行」与决策 4 的「不做软降权」已被
`2026-09-25-tier3-source-scheduling.md` 取代**（其余条款继续有效）· 关联：#334（wayfinder 决策票）、#327（路线地图）·
依据：`docs/wayfinder/2026-09-14-t3-tier3-mechanism-audit.md`、`docs/research/2026-09-14-t6-tier3-source-matching.md`、`docs/wayfinder/2026-09-14-t1-tier3-external-sources.md`

## 背景

tier3（用户自配订阅的第三方解析源）是官方直连失败后的唯一兜底。用户报告的「源会过期、
有并发限制、源太少」，经机制盘查发现**一半不是源站问题，是我们自己的调度**：

1. **解析腿源间严格串行，却共用一个 6s 整链预算**（`packages/core/src/tier3/tier3Api.ts:834-835`
   的双重 `for` + `await`；预算在 `packages/core/src/shared/sourceRouter.ts:314` 的
   `TIER3_BUDGET_MS = 6_000`，经 `:368` 的 `Promise.race` 施加）。前面几个慢源吃满预算后，
   **后面本可命中的好源一次都不会被请求**——即「多配源」是负收益，与用户直觉相反。
2. **单源默认超时 15s**（`tier3Api.ts:113` `DEFAULT_TIMEOUT_MS = 15_000`）**远超整链 6s 预算**，
   使预算失去约束力；且 `transport.ts:105` 的 `maxRetries=3`（超时类错误可重试，`:143-144`）
   会进一步放大实际耗时。
3. **搜索兜底腿完全没有预算**（`tier3Api.ts:646-651` 直接串行 `await`，无 `Promise.race`）。
4. **统计只覆盖解析腿**（`tier3Stats` 仅在 `:841/850-861` 自增），且被 source 过滤跳过的源
   **连计数都不进**（`continue` 在 `:836-840`，早于 `:841`）；纯内存 Map，重启清零。
5. **坏源无熔断、无退避、无自动停用、无并发上限**（`tier3Inflight` 只做同歌去重）。
6. **源归属过滤方向反了**：`tier3SourceSource`（`:807-819`）在 `source` 字段缺省时**按 URL
   host 猜源**（越权猜测），猜不出时**放行**（该守的没守）。而 `url-resolver` 这条腿
   **没有任何内容级校验**——`search-then-resolve` 有 `isExactMatch`（`:552-558`），
   `url-resolver` 只有域名白名单 + 字节嗅探（`:486-511`）。结果是：猜不出 → 该源被拿去解
   **任意源**的歌 → **跨源错播**。而 `tier3Api.ts:64-65` 的注释明确声称该字段正是用来防这件事的。
7. **`source` 值无白名单、无归一化**（`:253` 只 `assertString`）：`tencent`/`tx`/`QQ` 全通过校验
   但永不匹配，且搜索候选的 `sourceType` 被污染成该值（`:680`）→ 播放时 `decideRoute` 找不到
   客户端（`sourceRouter.ts:499`）→ 用户看到「可能为 VIP/无版权」（`playerStore.ts:382`），
   **错误提示指错方向**。

**嗅探的实测依据**（本次实测，可靠主机、多次重复）：首字节 0.39s（其中 TLS 握手 0.19s），
复用连接后 0.19s；**Range 从 12 字节到 1MB 的延迟无差别**。即嗅探成本 = 连接建立 + TLS +
一个 RTT，**与请求字节数无关**。另实测到有主机**完全忽略 Range**（`bytes=0-1023` 返回整个
10MB），此时 axios `arraybuffer` 会缓冲全量、撞满超时 → 好 URL 被误判为坏源。

## 决策

1. **调度：按源类型并行、源内串行。**（⚠️ 本条的「并行」部分**已被 `2026-09-25-tier3-source-scheduling.md` 取代为「不并行、只定序」**；「源内串行」继续有效。） 直连客户端与 tier3 解析链各自独立发起，**先拿到可播 URL 者胜**；
   tier3 内部仍沿源链**串行**（不并发打多个第三方上游，避免叠加限流）。
2. **超时阶梯：单源 2s 硬墙 + 整链 6s 软顶。** 源未显式配 `timeoutMs` 时的默认值由 15s **降为 2s**。
   搜索腿**补同款预算**（此前完全无预算）。
3. **嗅探：只对最终赢家嗅探一次**，独立超时 **1s**（不继承源 `timeoutMs`）。
   Range 维持 1KB（字节数与延迟无关，不做无意义改动）。
4. **坏源只做统计**，不做软降权 / 自动熔断 / 持久化（避免复杂度；用户取向为 less is more）。
   （⚠️ 本条的「**不做软降权**」一句**已被 `2026-09-25-tier3-source-scheduling.md` 取代**为
   「按会话内健康度只调整遍历顺序，可恢复、不缩减候选集」；「做统计」「仅会话内、不持久化」
   与「不做自动熔断」继续有效。）
5. **统计补全**：覆盖搜索腿 + 加失败原因 + 加 `skipped` 计数；**仅会话内**，不持久化。
6. **源归属：显式声明才过滤。** 删除 URL 推断；`url-resolver` 未声明 `source` 时**拒绝该源**
   （堵跨源错播通道）；`source` 值**加别名归一化**（`tencent`/`tx` → `qq` 等）。
7. **不做合规白名单**：订阅清单是用户自配，责任边界清晰；域名白名单必然滞后且会误伤合法源。

## 后果

- **`auto` 模式的语义发生变化**：CONTEXT.md 现定义为「直连优先、失败进 tier3 兜底」；
  并行后变为**先到者胜**，tier3 可能在直连本可成功时先返回（且可能是不同版本）。
  需同步更新 CONTEXT.md 的「来源开关」。**本条的落地放在第二阶段**（见下）。
- 「多配源」由负收益转为正收益（好源不再被慢源饿死）；搜索腿不再无上限等待。
- 跨源错播通道关闭；靠 URL 猜测的不稳定性消除（代价：未声明 `source` 的 `url-resolver` 用户
  需在清单里补一行，否则该源被拒）。
- 嗅探次数由「每个匹配候选一次」降为「每个返回 URL 的源一次」，搜索型源的多次嗅探被消除。
- 未解决（记录）：服务器忽略 Range 时的全量缓冲需**响应字节上限/提前中断**，依赖 transport
  是否支持；不支持则如实记录，不假装已解决。

## 分阶段落地

- **第一阶段（不改 `auto` 契约）**：决策 2/4/5/6 —— 超时阶梯、统计补全、源归属显式化与归一化。
  全部落在 `tier3Api.ts` 内部，不动 `resolvePlayableUrlRouted` 的调用形态。
- **第二阶段（改 `auto` 契约）**：决策 1/3 —— 并行调度与赢家嗅探。需同步改 CONTEXT.md，
  并在 PR 中显式标注语义变化。

## 备选与否决

- **软降权 / 自动熔断 / 持久化统计**：否决。理由：复杂度与收益不成比例；用户自配清单场景下
  「源临时抖动」不应变成「永久失效」，且用户需自行处理而非被系统代劳。持久化还会让昨日状态
  污染今日判断。
- **合规白名单硬拦**：否决。理由：白名单永远滞后 + 误伤合法源自配；且会带来虚假安全感。
- **缩小 Range 到 12 字节**：否决。实测延迟与字节数无关，改动无收益。
- **嗅探延后到播放后再验证**：否决。会把失败推迟到更难解释的时刻（无声播放优于报错是错觉）。
