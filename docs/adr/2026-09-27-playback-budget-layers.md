# 播放链路的时限层次：单请求超时 / 墙 / 预算 / 闸门排队（#399）

- 状态：已接受
- 日期：2026-09-27
- 相关：#399（本票）、#389（直连 3s 墙）、#392（播放期取证）、#365（死源吃满预算）、
  #388（分源耗时实测）、#408 / #413（出网闸门与 AbortSignal 贯通）、#335（播放体验目标）
- 取代/追认：追认 `2026-09-25-tier3-source-scheduling.md` 决策 7 的**按 kind 分档单源墙**
  （取代 `2026-09-14-tier3-scheduling-and-source-ownership.md` 决策 2 的扁平单源 2s），
  并把该 ADR 决策 3「嗅探独立 1s」的**定位**落成实现语义：嗅探不占单源墙。

## 背景

播放链路上的时限旋钮有 40 余处，散在 6 个文件里，而「超时」这个词被四个不同层次共用：
单请求超时、墙（腿的硬上界）、预算（整条腿共享的池子）、以及 #413 新加的出网闸门排队。
三处文档与代码不一致、一处核心值没有决策记录：

1. `AGENTS.md` / `CONTEXT.md` 写「直连解析腿有独立 3s 墙钟……对直连 URL 做一次时长取证」，
   读者会理解为「直连腿 ≤3s」；但取证发生在墙**之外**，成功路径上界是 **3s + 1.5s = 4.5s**，
   而 #335 把「点歌 → URL 就绪 P95 ≤3s」写成目标——两句话各自成立，合起来看就是口径不清。
2. `2026-09-14` ADR 决策 2（扁平单源 2s 墙）与 `2026-09-23` ADR 决策 5（单源 2s 硬墙）
   已被 `2026-09-25` 决策 7 取代为按 kind 分档（2s / 2.5s），但旧文未批注。
3. 同一 ADR 决策 3 写「只对最终赢家嗅探一次」，实现是「每个产出 URL 的源各一次、且嵌在单源墙内」。
   由于源内串行、第一个探通即交付，跨源上两者**已经等价**；真正的偏差是**嵌在墙内**——
   两步源的 2.5s 墙里含着 1s 嗅探，搜索 + 解析只剩 1.5s（#388 实测 2047ms 的成功路径被切）。
4. 直连 3s 墙的出处只有 #389 票正文里的一句「建议」，没有 ADR——一个决定成功路径上界的值
   不该只存在于 bug 票的讨论里。

## 决策

1. **四层词汇与单点常量表。** 跨模块共享的墙 / 预算 / 传输默认值集中在
   `packages/core/src/shared/playbackBudgets.ts`，每项注明所属层、谁能覆盖它、以及它是否
   被上层的墙盖住（死值）。四层定义：单请求超时（传输层/源自持，一次 HTTP 尝试）；
   墙（调度层，腿的调用方持有，到点即放弃**并 abort 底层请求**）；预算（编排层，整条腿共享、
   多源分食，耗尽按「迟到命中丢弃」结算）；闸门排队（transport 接缝的并发节流，**不是超时**）。
2. **直连腿的预算口径如实写：墙 3s 只管「拿到 URL」。** 无权威时长的源（`resolveUrlInfo` 只实现了
   netease / soda，其余五源拿到的 URL 不带时长字段）拿到 URL 后，在墙**之外**做一次时长取证，
   独立 1.5s 上限；故**成功路径上界 = 4.5s**，失败路径仍是 3s。#335 的「P95 ≤3s」口径明确为
   **URL 就绪**、不含取证。**不改任何值**（3s / 1.5s 原样），只把口径写进 ADR 与活文档。
3. **嗅探不占单源墙。** 单源墙的计时内容 = 「搜索 + 解析」；嗅探（一次 64KB Range + 头解析）
   按 ADR-0014 决策 3 独立 **1s** 计时，且**计入整链 6s 预算**。实现 = 可暂停墙钟
   （`tier3Api` 的 `SourceClock`）：嗅探期间停表、按剩余额度续走；探测缓存命中的嗅探不暂停
   （无网络）。于是单源上界从「2.5s 含 1s 嗅探」变为「2.5s + 1s」，整链上界仍是 6s。
4. **墙值不动、公开旋钮只留一个。** 单源墙按 kind 分档（url-resolver 2s / search-then-resolve 2.5s）；
   清单里的 `timeoutMs` 是**唯一面向用户的墙值旋钮**，且只能**收紧**（`effectiveSourceTimeout`
   的 `min`）；不新增可编辑设置项——若要可见性，只在设置页「播放诊断 / 第三方解析源」区
   **只读**展示每源的生效值。
5. **闸门排队消耗墙与预算。** 墙的计时器在调用方手里、请求却在闸门里排队，所以排队时间照走墙
   与预算（这正是 #365「死源吃满预算」的另一副面孔）。闸门自身不感知墙钟（沿用
   `2026-09-26-outbound-request-governance.md`）。

## 备选与否决

- **把取证并入 3s 墙**（墙到点即砍掉取证）：否决。取证的用途是「标记试听片段」，被砍掉就走
  fail-open——30 秒试听会被当完整版播出去，用户零感知。用 1.5s 的极端尾巴换标记可靠，划算。
- **墙放宽到 4.5s 并把取证计入**：否决。等于作废 P95 目标，换来的只是表述简洁。
- **按字面重做「只对最终赢家嗅探一次」**：否决。源串行 + 第一个探通即交付，跨源上已等价；
  真正该改的是「嵌在墙内」，改完就是决策 3。
- **删掉嗅探**（「反正官方 CDN 很快」）：否决。官方直连腿没有这种字节嗅探，有嗅探的只有 tier3，
  而 tier3 的 URL 来自第三方源、不是官方 CDN。删掉等于把 `text/html` 错误页链接与试听片段
  直接交给播放器：失败被推迟到更难解释的时刻，与 ADR-0014 已否决的「嗅探延后到播放后」同因。
- **把嗅探挪到设置页做源健康检查**：否决。探测缓存的键是**具体 URL**，每次播放解析出的 URL
  不同，设置页那条链验不到这次要播的那条；设置页能做的是源级健康（通/不通 + 耗时），属 #408 面。
- **清单 `timeoutMs` 升为设置页可编辑旋钮**：否决。kind 硬墙会把它 `min` 死（只能收紧），
  可编辑只会让用户以为自己能放宽。
- **直连源 8–30s 超时收敛成单一常量**：否决。会白丢离群源容忍度（#388 实测存在 20.7s / 22.3s
  的离群源）；本轮只把「解析腿死值」的事实注释到位，不改值。

## 后果

- 活文档与代码口径一致：`AGENTS.md`、`CONTEXT.md`、`docs/agents/architecture.md`、
  `docs/agents/tier3-manifest.md`，以及 `2026-09-14` ADR 决策 2/3、`2026-09-23` ADR 决策 5
  均已批注指向本 ADR。
- 旧票 / 旧 ADR 里的行号引用全部失效（例：`sourceRouter.ts:331` 的 `DIRECT_WALL_MS` 已移入
  常量表）；引用常量名而非行号成为约定。
- 单源上界由 2.5s 变为 3.5s（两步源 = 2.5s 墙 + 1s 嗅探），整链上界仍 6s；健康度「截尾样本」
  的降权口径（w=0.5）不变，但截尾发生的时点后移。
- **未落地（如实记录）**：闸门排队上限与「排队耗时入 trace」未做——需要先跑一段 #408 的闸门
  指标（`getOutboundGateStats`）再定上限；直连源 8–30s 超时值仍分散在各源文件，未收敛。
- 残余风险：单源上界放宽后，慢源在整链 6s 内的分食比例会变（谁能拿到预算的分布变化）——
  整链上界未变，但需用播放 trace 与闸门指标复核是否引入新的饿死形态。
