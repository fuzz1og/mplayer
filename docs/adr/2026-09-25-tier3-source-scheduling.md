# tier3 源的会话内调度：健康度定序、首次解析即初始化、全局在飞上限

日期：2026-09-25 · 状态：已接受 · 关联：**#379**（本决策票）、#388（分源命中率与耗时实测，本决策的数据依据）、#335（D4/D5 版本分流）、#389（直连腿无墙，影响前置延迟） ·
依据：`docs/research/2026-09-24-per-source-hitrate-latency.md`（#388 实测）、`docs/wayfinder/2026-09-21-t5-playback-chain-baseline.md`（t5 基线 §2.4/§2.5）、ADR-0014（本 ADR 取代其决策 1 与决策 4 各一句）

## 背景

tier3 解析腿的源之间**严格串行、共用一个 6s 整链预算**（ADR-0014 背景第 1 条）。t5 §2.5
的受控实验证明「源顺序」是链路上量级最大的单一杠杆：同一首歌、同一网络，仅改顺序——
真实顺序 6077ms **拿不到 URL**，好源前置 1057ms **命中**。

ADR-0014 决策 1 的方向是「按源类型并行、源内串行」，但**只落地了第一阶段**（决策 2/4/5/6：
超时阶梯、统计补全、源归属显式化）；**第二阶段（并行调度与赢家嗅探）至今未做**，且它与
CONTEXT.md 的 `auto` 语义变更绑定，需要独立决策。

#379 要决的是「形态」。本轮由 #388 补齐了实测数据，得到四条**直接推翻原假设**的事实：

1. **「解析腿源排序」不存在。** `resolveRoutedInner` 用 `decideRoute(song.sourceType, …)`
   按歌自己的音乐源取**唯一**客户端（`sourceRouter.ts:513-520`）——一条歌在直连解析腿上
   **只有一个候选**，没有「先问谁」的空间。真正可互换、需要定序的只有 **tier3 订阅源之间**
   （多个源可以服务同一首歌）与**搜索页的跨源搜索**。#388 报告里的「解析腿排序」实为
   「哪家源当曲库更值得」，属搜索页选源，不是解析调度。
2. **源的可互换性差异是数量级的。** #388（136 首 / 7 源 / 816 次搜索）实测精确匹配率：
   kugou 82.5% / qq 79.8% / soda 67.5% / netease 63.2% / migu 55.0% / **kuwo 11.4% /
   qianqian 0.8%**；**前 3 源联合覆盖 89.0%，第 4 源只加 1.4pp**，kuwo/qianqian 在 136 首
   里**零独有贡献**。耗时同样分化：kugou P50 103ms，soda P50 867ms，qianqian P99 4152ms。
3. **贴墙率的真实分布说明「墙」拦的是离群源，不是正常路径。** 搜索腿对 2s/3s/6s 贴墙率
   **几乎全 0%**（仅 qianqian 5.0%）；解析腿仅 soda 6.3%（一次 12.5s）。而两步源
   （search-then-resolve）的三段网络串行在**同一个单源墙内**（`withSourceDeadline` 包住
   `resolveTier3Candidate`，后者内含搜索 + 解析 + 嗅探），实测**一次 2047ms 的成功路径**
   与**一次 2081ms 被 2s 墙切掉**——2s 对两步源是**结构性偏紧**，不是偶发抖动。
4. **并发会放大「多首并发解析」这个既有乘数。** 串行下上游在飞数 = 在飞歌曲数；并行后
   = 在飞歌曲数 × 每首并发源数。而**跨歌在飞上限今天不存在**（只有 `tier3Inflight` 的
   同歌去重，`sourceRouter.ts:405-437`），批量下载（并发 3，`DEFAULT_MAX_CONCURRENT`）、
   快速连续切歌、失败跳歌链都能同时压多条解析。#388 还实测到 **qq 搜索在 200ms 间隔下
   12 次里 10 次返回 `code=2001`**（400ms 则 14/14 成功）——单源速率上限是真实约束。

另有一条既有草案（本地分支 `docs/tier3-source-health`，未合入、未开 PR）提出的
「被动统计健康度排序」方向与本文一致，但它的**主动性判断相反**（该草案把主动探测列为否决项，
理由是「零额外请求」），且在冷启动时只能退回清单顺序——而用户清单里坏源是**长期留档**的，
第一条 QQ 歌照样可能全灭。本文取代其方向。

## 决策

1. **不并行。tier3 解析腿维持源内串行，只调整遍历顺序。** ADR-0014 决策 1 的「并行调度」
   与「赢家嗅探」**不落地**：解析腿的源之间可互换，但并发会（a）放大跨歌并发乘数、
   （b）在第三方主机上叠加限流（#388 已实测 qq 的 2001 速率墙）。**顺序已经能拿到并行的大部分收益**
   （前 3 源 89.0% 覆盖），而并行的代价是多条在飞请求——不划算。
2. **会话内单一健康度，只定序不筛选。** 新增纯函数模块 `packages/core/src/shared/sourceSchedule.ts`
   （`noteSample` / `scoreOf` / `orderSources` / `beginInit` / `isInitialized` /
   `clearSourceSchedule`）。**不按目标音乐源分桶**——第三方源的健康度属于「这台上游主机今天怎么样」，
   与客户端拿的是哪家直连源的歌无关（源归属已由 ADR-0014 决策 6 的 source gate 保证）。
   状态为模块级 Map（会话内、不落盘），与 `tier3Stats` / `prefetchCache` 同取向。
3. **排序纪律：只改顺序，绝不缩减候选集。** 排序前后「可用源集合」逐元素相等；所有可用源
   **仍会被尝试**；连续失败 N=2 才降级、成功一次即回归；**无样本时完全回退清单顺序**
   （冷启动零行为变化）。这是防「静默不播」的红线。
4. **初始化 = 第一次 tier3 解析本身，不额外发探测请求。** 第一首进 tier3 的歌以「初始化形态」
   解析：交错起手（H=600ms）、在飞 ≤2、单源墙放宽到 **4s**（比常态宽，因为「用墙测墙」会把
   被测源截成 censored 样本），采到的样本写入方案。**收尾即将本次交付的候选返回**，不阻塞播放。
5. **整个会话只有一个并行窗口（单飞）。** `beginInit()` 只对第一个够格的调用返回 true，其余
   一律按方案串行。这是对「第一首没解析完就切第二首」的正面回答：第二首**不开第二个并行窗口**，
   按清单顺序串行起一条——把最坏并发从「切歌数 × 2」压回「2 + K」。
6. **样本三类分流，截尾与放弃不进分。** 完整观测（源自己在墙内返回）正常计分；**截尾**
   （`SOURCE_TIMED_OUT`，被单源墙切掉）单独一档、降权 w=0.5（它不是「源坏了」，是「我们没测到」——
   实测 S5 类两步源 2617ms 命中，2s 墙必然切它，按 error 记会把慢而好的源永久判死）；
   **放弃观测**（调用方预算用尽/用户切走）记 trace 供排障，**不进健康度**——它反映的是用户切得快，
   与源无关。计分含耗时：`reward(hit, ms) = 1 - min(1, ms/3000)`，否则 987ms 命中的源与
   2617ms 命中的源同分。
7. **单源墙按 kind 分档：url-resolver 2s / search-then-resolve 2.5s，3s 为安全余量。**
   依据：两步源三段串行在同墙内（实测 2047ms 成功、2081ms 被 2s 切）；一步源 2s 余量充足
   （S1 max 1264ms、S2 max 1267ms）。清单 `timeoutMs` 仍**只能收紧不能放大**。
   **补记（2026-09-25，落 #394 / PR #395 验收）**：本条原文只定了「硬墙上限」，
   没定**不写 `timeoutMs` 时的默认值**；实现沿用 ADR-0014 的扁平 2s，于是本条自己的理由
   （「2s 会切掉实测 2047ms 的成功路径」）对任何没手写 2500 的清单**依然成立**——分档形同虚设
   （验收时用户的通用兜底条目写 `timeoutMs: 2000`，2.5s 的墙一次都没被碰到）。
   现定：**默认值同样按 kind**（不写 = 该 kind 的硬墙；显式写仍只收紧）。取舍如实记录：
   不写的两步源从此多吃 0.5s 整链预算，挂死的慢源更容易挤掉后面的源——这是拿「不写就正确」
   换「最坏情况整链多耗 0.5s/源」，在 6s 整链预算下可接受（决策 9 的搜索腿预算独立，不受影响）。
8. **跨歌全局在飞上限 K=3。** 挂在 `tier3ResolveShared`（`sourceRouter.ts:415`）外层，FIFO 排队；
   **排队期间各调用方自持预算**（不得让排队时间计入 6s，否则切歌场景 P50 反而退化）。取 3 的
   依据：与既有下载并发 `DEFAULT_MAX_CONCURRENT=3` 同量级，且第三方主机通常 2–3 台，
   「每台一条在飞」即可。
9. **搜索腿与解析腿的预算维持各自独立，不共享 deadline。** 二者语义不同（搜索是「尽量找全」、
   耗尽返回已收集的部分候选；解析是「要么拿到 URL 要么失败」），合成一个 deadline 会让
   搜索腿的部分语义泄漏进解析腿。
10. **修正 CONTEXT.md 与清单文档的口径，不改 `auto` 契约。** 本决策不动 `auto`/`direct`
    的语义（ADR-0014 第二阶段的那条契约变更**不做**），只改 tier3 内部的遍历与墙值。

### 对 ADR-0014 的取代范围（正面处理，不重写已接受的 ADR）

- **决策 1「调度：按源类型并行、源内串行」**：其中「**源内串行**」继续有效；「**按源类型并行**
  与赢家嗅探」（即 ADR-0014 的第二阶段）**被本 ADR 取代为「不并行」**。
- **决策 4「坏源只做统计，不做软降权」**：其中「坏源做统计」「仅会话内、不持久化」继续有效；
  「**不做软降权**」一句**被本 ADR 取代**为「按健康度只调整遍历顺序（可恢复、不缩减候选集）」。
  本决策刻意收窄：**无自动熔断、无永久禁用、无持久化、不删除任何源**。
- ADR-0014 的其余条款（决策 2/3/5/6/7 与后果节）**不受影响**，继续有效。

## 备选与否决

- **全并发打所有可用源**：否决。放大跨歌并发乘数（切歌场景 = 歌曲数 × 源数），且 #388 实测
  单源速率墙真实存在（qq 200ms 间隔 10/12 失败）。
- **交错对冲但不设全局上限**：否决。切歌场景下每首仍各开一个窗口，最坏并发 = 切歌数 × 2；
  单飞 + K 才是完整答案。
- **按目标音乐源分桶定序**：否决。第三方源的健康度与直连源无关；且 source gate（ADR-0014
  决策 6）已在源头保证不会拿 A 源的 id 问 B 源。分桶是重复保护。
- **直连腿 ↔ tier3 腿并行（先到者胜）**：不做。它改 `auto` 契约、与跨源救回语义（#386 已关闭）
  纠缠，属独立决策；本 ADR 明确不碰。
- **整链 6s 预算按源静态分摊（deadline 均摊）**：否决。并行不做之后它仍会**切掉慢的好源**
  （两步源 2047ms 的成功路径会被分摊后的短窗误伤）。
- **健康度持久化 / 自动熔断 / 永久禁用**：否决，沿用 ADR-0014 决策 4 的理由（源临时抖动
  不应变成永久失效；昨日状态不应污染今日判断）。
- **主动探测（加载时并行探测/手动测速）**：否决。初始化复用**第一首歌本来就要做的那次解析**，
  零额外请求；额外的主动探测不带来新信息。

## 后果

- **「多配源」从负收益转回正收益**：好源不再被坏源饿死；冷启动首次遇到某首歌仍按清单顺序
  （无样本），样本积累后重排。
- **零额外请求、零新契约**：初始化不是新请求，方案是会话内内存，不改清单 schema、不改
  `auto`/`direct` 语义、不新增 IPC。
- **新增一个可单测的纯函数模块**：`sourceSchedule` 无 I/O、无持久化，三条不变量可直接断言
  （候选集不变、冷启动顺序不变、每会话至多一个并行窗口）。
- **跨歌并发有了上界**：K=3 把「批量下载 × 快速切歌 × 失败跳歌」的叠加封顶，是防限流的
  结构性保障，而非调参。
- **残余风险（如实记录）**：
  - 「用墙测墙」——初始化窗口的 4s 墙仍是人为截断，censored 样本按降权处理但不承诺无偏；
  - EWMA（α=0.3）可能把一次抖动误判为「坏」，靠 N=2 才降级 + 成功即回归 + 会话内自然遗忘缓解，
    不承诺零误判；
  - **本决策的墙值与会话内排序参数应在 #389（直连腿加墙）落地后复核一次**——那条腿决定
    tier3 的**前置延迟**上界，两段的关系要重算。
  - tier3 订阅源是用户自配，**本方案的冷启动行为完全取决于用户清单顺序**；「多配源」的
    正收益只在样本积累后体现。
- **文档同步（随实现做，不在本 ADR 内）**：`docs/agents/tier3-manifest.md` 的「单源 2s 硬墙」
  表述按 kind 分档改写；`CONTEXT.md` 的「tier3 订阅源」条补一句「遍历顺序按会话内健康度动态调整」。
  这两处描述的是**当前契约**，故只在对应实现（1.8.x 的墙值分档与会话内定序）落地时同步，
  本 ADR 提交时不预改，避免活文档记录未落地的行为。

## 落地分期

- **1.8.x · 第一批（已落地）**：决策 7（按 kind 分档墙）与决策 8（K=3）——纯参数与防限流补丁，
  **不动调度形态**，可独立 PR 验证（#394 / PR #395）。
- **1.8.x · 第二批（票 #398）**：决策 1–6（不并行 + 会话内定序 + 单飞初始化 + 样本三类分流）——改调度逻辑。
  **2026-09-25 维护者决定：由 1.9.0 改回 1.8.x。** 原分期把它放在 1.9.0 的理由是「改调度逻辑」，
  而本仓版本闸门的判据是「**要不要新 UI**」（不是工作量）：本片完全落在 core 调度内部、无 UI 面，
  按闸门本应属 1.8.x —— 原分期是判据用错，此处纠正。落地时仍需与已实现的 #389（直连腿 3s 墙，
  决定 tier3 的**前置延迟**上界）一起复核墙值与排序参数（见「后果」节的复核项）。
