## 0. 一页结论（决策相关）

> **本票存在第二份并行报告**（同票并发测量）：`docs/research/2026-09-25-per-source-hit-rate-and-latency.md`（218 首、口径偏向榜单单源）。两份在 netease/migu 上数字不同，原因已定位为**样本口径差异**（§6）——不是测量错误。**结论请以两份中「稳健」部分合并使用**：两端口径一致（kugou 恒第一、qianqian/kuwo 恒末位），中段（migu/soda/netease）随口径翻转，需先定取景。

1. **搜索腿没有一个是慢的，贴墙率全部 ≈0%**。七源搜索 P50 88–867ms、P99 ≤1.3s，**对 2s 墙的贴墙率 0.0%**（qianqian 的 5.0% 是 4.1s 离群，见 §3.5）。→ **#379 Q4「搜索腿是否补同款预算」的数据答案：补 6s 同款预算对正常源没有约束力；有约束力的是一把 ~1.5–2s 的单源搜索墙**（只需拦住离群源）。
2. **源之间曲库覆盖度差一个数量级——排序比预算重要得多**。搜索腿精确命中率：kugou **82.5%** / qq **79.8%** / soda **67.5%** / netease **63.2%** / migu **55.0%** / kuwo **11.4%** / qianqian **0.8%**。
3. **三个源（kugou→qq→soda）就覆盖 89.0% 的样本**，第四个源（netease）只加到 90.4%，**剩下三个源（migu/kuwo/qianqian）合计只加 0.8pp**（90.4% → 91.2%）。→ **遍历顺序的收益在「前三个源」，后四个源近乎零边际贡献。**
4. **必须扫完列表，但增量只有 5.8pp**。只看 top1 = 45.5%，扫完整个列表 = 51.2%（相对 +12.7%）。精确匹配的最佳 rank P90 = **1**、max = **22**；**91% 的命中就排在第 0 位**，排到第 5 位之后的只有 12/418。→ 「扫完列表」便宜且必需；扫到第 10 位即覆盖 99% 的命中。
5. **解析腿（直连）与搜索腿是两种完全不同的源，排序不能共用一张表**。本源解析命中率：kuwo **100%** / soda **100%** / netease 50% / migu 50% / qianqian 31.3% / **qq 0% / kugou 0%**（本轮故障，见 §3.6）。
6. **两步源不比一步源慢**。同一批 QQ 歌、同样单源隔离：两步源 S3 命中 11/12、P50 **1070ms**；一步源 S1 命中 10/12、P50 **1199ms**。两步源的搜索腿 P50 **489ms** + 解析腿 P50 **524ms** ≈ 1013ms，**两步不是「慢一倍」，而是「多一跳 ~0.5s」**。→ 支持 #379「按源类型给墙」：2s 墙对两步源偏紧但仅差 ~0.5s，2.5s 更安全。
7. **一步源 S1 的尾部明显更重**：P50 1187ms 但 **贴墙率（≥1.7s）17%（2/12）**，其中 1 次是**单源硬墙 2000ms 超时**。→ 一步源 `url-resolver` 是「要么快、要么贴墙」的双峰，比两步源更需要硬墙兜底。

**给 #379 的排序建议（数据，不替它决定）**：kugou → qq → soda → netease 是第一梯队（前三个够，第四个可选），migu 视场景保留，kuwo / qianqian 作为**目标源**应降到最低优先级或移出遍历集合（kuwo 11.4%、qianqian 0.8%）。**这与预览测量（#388 评论：qianqian 作目标源 0/5）一致，但现在有其他六源的完整分母。**

| 腿 | 源 | n | P50 | P90 | max |

**读法**：

1. **两步源 ≈ 两步的「半段之和」，不比一步源慢**：S3 的 489 + 524 = **1013ms**，实测 P50 1070ms；S1 单跳 **1126ms**，实测 P50 1199ms。差异主要来自 S1 上游单跳解析本身就要 ~1.1s。
2. **两步源的抖动更小**：S3 的 max/P50 = 1.46；S1 的 max/P50 = 1.12 但**贴墙率 17%**（有一首《晴天》直接撞 2s 单源硬墙超时）。一步源是「要么 1.0–1.2s 命中、要么 2.0s 贴墙失败」的双峰。
3. **S1 的 5 次 MISS 里有 4 次是护栏拒绝（`guardRejected`），1 次是单源硬墙超时**（`lastError`: "单源硬墙 2000ms 超时"）——即 S1 的「64% 命中率」里有一部分是**护栏把 Live/翻唱/MV 版挡掉了**，不是源不交付。当目标歌本身是 Live 版时，护栏会合理拒绝（这是安全性而非缺陷）。
4. **本机真实订阅单源成绩（脱敏）**：S1（`url-resolver`@qq）**9/14 = 64%**、P50 1187ms、贴墙 7.1%；S2（`url-resolver`@netease）**14/14 = 100%**、P50 47ms；S3（`search-then-resolve`）**14/14 = 100%**、P50 91ms。→ **S2/S3 快且稳，S1 慢且只有 64%**（又一次「顺序决定成败」的直接证据，与 t5 §2.5 同向）。

## 3. 附带的、对 #379 有直接影响的发现

### 3.1 三个源就够——但「够」的是搜索腿，不是解析腿

搜索腿前 3 源覆盖 89.0%，但**解析腿的源排序必须另算**：解析腿只对**原生歌**有效（跨源解析 = A，已在 #386 否决）。所以 #379 需要**两张排序**：

- **搜索腿排序**（谁去搜）：kugou → qq → soda → netease → migu →（kuwo/qianqian 最后或移除）
- **解析腿排序**（谁去解）：kuwo → soda → migu → netease → qianqian（qq/kugou 本轮不可用，见 §3.6）

### 3.2 「扫完列表」的精确截断点

最佳 rank 分布显示：**扫到第 10 位就覆盖 99% 的命中**（412/418），第 11–22 位只多 6 例。→ 若 #379 需要为搜索腿设「扫多少条」的上限，**10 条是数据上的膝盖点**（这不是墙，是结果数组的遍历深度）。

### 3.3 空 URL 是「安静失败」——预算设计必须覆盖它

136 次解析里 **74 次空 URL、0 次抛错**。空 URL 的耗时极短（netease 空 URL 子集 P50 ~44ms）。→ 若 #379 按「超时」设计墙，会**漏掉这条「快而空」路径**：它不触发墙、不抛错，但源事实上没交付。这是 #379 预算分摊要区分「慢」与「空」的理由。

### 3.4 QQ 搜索风控：code=2001，恢复窗口 > 30s

测量中 QQ 搜索两次触发 **QQ 搜索 code=2001**（`qqDirect.ts:441` 抛错）。实测边界：

| 请求间隔 | 结果 |
| --- | --- |
| 400ms（冷却后首轮 burst，14 次） | **14/14 成功** |
| 200ms（冷却后 burst，12 次） | **2/12 成功**（10 次 2001） |
| 600ms（紧接上一轮 burst，12 次） | **7/12 成功**（5 次 2001） |
| 2000ms（主测量，114 次跨 ~4 分钟） | **114/114 成功** |

- **2001 是短窗口限流，不是封禁**：60–90s 冷却后完全恢复。
- **不要把它当「源不可用」**：本轮按「连续错误 ≥8 次即停止加压」处理，两次触发都在冷却后恢复，**没有为了凑样本继续站**。
- → 对 #379 的含义：**QQ 是搜索命中率第二高的源（79.8%），但它的可持续速率最低（约 ≥1.2s/请求）**。若 #379 把多源搜索改成并行，**QQ 的并发/速率上限会成为约束**——这不是「加源」问题，是单源速率问题。

### 3.5 qianqian 的双峰离群（搜索腿）

qianqian 正常时 P50 136ms / P90 164ms，但有 **6/120（5.0%）落在 4.07–4.17s**（几乎同一数值，疑似固定重试退避）。→ 它是**唯一需要单源搜索墙的源**；一把 2s 墙即可把 P99 从 4152ms 压到 ~200ms 量级，且**不损失任何命中**（那 6 次全部是空结果或无关结果，qianqian 整体命中率只有 0.8%）。

### 3.6 【计划外·高优先级】qq / kugou 直连解析本轮 100% 失败

> 这不是 #388 票面要求，但它是本轮最有决策价值的发现，且直接影响 #379「解析腿」的源排序。**如实记录，不掩饰。**

| 源 | 现象 | 范围 | 根因证据 |
| --- | --- | --- | --- |
| **qq** | `resolvePlayableUrl` **恒返回空串**（22/22 样本，另 10/10 热榜歌复核，全部空） | 100% | GetVkey 返回 `code:0`，但 `midurlinfo[0].purl` = ""、`result: 104003`、`subcode: 1`、vkey: "" —— **上游判定无播放权限** |
| **kugou** | `resolvePlayableUrl` **恒返回空串**（22/22 样本，20 首热榜复核，全部空） | 100% | kugou 官方 tracker CDN 的 v2 直链端点 返回 {"status":2,"trans_param":{...}} —— **再无 data.url 字段** |

**已做的排除**：

- **不是探针 artifact**：不注入 transport（走 core 默认 axios 实现）复核，qq 0/10、kugou 0/20，结果一致。
- **不是 cookie 问题**：kugou 用**全新生成**的设备 cookie 与**用户持久化 cookie** 结果完全相同。
- **不是参数问题**：cmd=21/25/26、behavior=download/play、version=1/2/1000/9108、br=hq/320 全部返回同一 `status:2`；带浏览器 UA/Referer/Cookie 亦同。
- **不是 TLS 指纹缺失**：两者出网都经 core transport（未被要求注入指纹 agent），且**请求本身 200**——是响应内容问题，不是握手问题。
- **与既有 issue #172 不同**：#172 是「QQ **热榜**歌 id 是数字、不是 songmid → GetVkey 空」。本轮用的是**搜索结果**里的歌（id 就是 songmid）与**热榜歌**，两者都空，**说明不只是 id 语义问题**。

**影响**：#379 的「解析腿」源排序目前**不能用 qq/kugou**；本机现有三个 tier3 源里 S1（`url-resolver`@qq）正是补这个洞的（64% 命中、P50 1.19s）。这解释了 t5 §2.4 的观测，也说明**「直连优先」在 qq/kugou 上是名义的**。

**建议**：这是**独立的直连腿缺陷**，不属于 #379 的调度范畴，**不并入 #379**。已在报告外单独提示主会话按流程建票（本票不改产品代码、不建不属于本票的票）。

### 3.7 【机制缺陷】`direct` 模式 + 直连抛错 = tier3 完全不参与

复现（合成 harness，非真实源）：

| sourceMode | 直连行为 | 结果 | tier3 stats |
| --- | --- | --- | --- |
| `direct` | 抛错 | **异常上抛** | {}（tier3 一行没跑） |
| `direct` | 返回空串 | 空 URL | S1/S2 `skipped`=1、S3 `misses`=1 |
| `auto` | 抛错 | 异常上抛 | S1/S2/S3 全跑 |
| `auto` | 返回空串 | 空 URL | S1/S2/S3 全跑 |

- 与 t5 §1 的「`direct` 只拦「直连抛错」分支」**方向一致**，本轮实测确认抛错在 `direct` 下确实不进 tier3（`sourceRouter.ts:556` 的 if (route.mode === 'direct') throw err;）。
- **本轮 136 次解析 0 次抛错**，所以这条缺陷**没有污染任何主测量数字**；但它意味着**用户切到 `direct` 时，QQ/Kugou 这类「会抛错而非返回空串」的源将完全失去 tier3 兜底**。
- 归 #379（它管调度）还是独立票，由主会话判断；本票只记录现象与复现。

## 附录 A · 复现方法

**环境**：Node v24.10.0；npm run `core:build` 生成 `packages/core`/dist；`packages/core`/dist/index.js 直接 import（与移动端同入口，无需 Electron）。

**探针骨架**（一次性、未入库，/tmp 下）：

1. **传输 tap**：`setTransport`(myAxiosTransport) 注入与 core 默认实现同语义的自持 axios 传输（**必须自持**——注入的回调里不能再调 core.request，否则无限递归），记录每次原始尝试的 {host, path, status, ms}；`setTransportRetryOptions`({maxRetries:3, baseDelayMs:100}) 与 core 默认一致。
2. **注册官方源**：`registerDirectClient`(neteaseDirectClient / qqDirectClient / kugouDirectClient / kuwoDirectClient / miguDirectClient / qianqianDirectClient / sodaDirectClient)；`setSourceModes`（七源全 `direct`）。
3. **搜索腿**：对每首歌、每个目标源调 `searchSongsRouted`(`name + " " + artist`, 1, target)，用 `isExactMatch`({name, artist}, candidate) 判命中并记 rank。
4. **解析腿**：对原生歌调 `resolvePlayableUrlRouted`(song)，URL 非空即命中。
5. **tier3 单源隔离**：从用户 `storage.json` 读真实订阅，`setTier3Subscriptions`([{...sub, manifest:{version:1, sources:[S[i]]}}]) + `setTier3Resolver`(`createTier3Resolver`()) + `setTier3Enabled`(true)，每次 `clearPrefetchCache`() + `clearTier3Stats`()。
6. **两步/一步对照**：同一批 QQ 歌分别挂 S1 / S3 单源，按 path 归因搜索腿（搜索跳）与解析腿。

**礼貌与风控**：并发 ≤2，请求间 400ms（QQ 2000ms），tier3 隔离 1000ms；**连续错误 ≥8 次即停止该源**（本轮 QQ 触发的 code=2001 两次都在冷却 60–90s 后恢复，未继续加压）。

**数据文件**（本地，未入库）：/tmp/results-main.json（搜索+解析）、/tmp/results-tier3b.json（tier3 单源）、/tmp/results-2step.json（两步 vs 一步）、/tmp/results-searchleg.json（tier3 搜索腿）、/tmp/http-log.json、/tmp/summary.json。

| 口径 | 排序 |

- **中段会翻转**：**migu 在「主流原唱」里排第 3（85.7%）、在「长尾/翻唱」里掉到倒数第 2（7.7%）**；soda 与 netease 也在中段互换。→ **「migu 该排第几」不是数据能定的，取决于用户听的是主流还是长尾**——#379 若要固定顺序，需要先定「以哪类歌为主」，或者让中段顺序随场景切换。

- 本报告的 §2.2 全样本名次是**对 136 首混合样本**的结果；若 #379 的取景偏热榜主推（主流原唱），migu 的优先级应上调。**这是「样本口径」而非「测量错误」导致的差异。**
