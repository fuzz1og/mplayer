## 一页结论（对 C/C′ 可直接用的 8 条）

1. **没有任何在线源项目「提前把 URL 全量入队」**。全是「MediaItem 只放 id/元数据 + URL 按需解析」，粒度三种：onAddMediaItems（Jellyfin，成立仅因服务端 URL 带 ApiKey 且不过期）/ resolveOnTransition（AntennaPod 曲末解析单条）/ **resolveDataSpec**（Metrolist、SimpMusic、InnerTune、ViMusic —— 网络源的正解）。
2. **但我们的 resolver 在 JS/core，后台跑不了** → 不能照抄 resolveDataSpec。RN 宿主的必然形态是「**小窗口预解析 + 绝对过期时间 + 原生过期跳过 + JS 醒来补窗**」——这是与所有对照项目最本质的区别，也是本调研最大的收获。
3. **队列所有权两派**：整条 playlist 交给播放器（UAMP/AntennaPod，只在 URL 已知且长期有效时成立）vs「播放器只持当前一首 + 原生推进」（Retro/NewPipe/Transistor）。我们的 URL 未知 → **必然是后者**；C′ 要补的正是这套，C 要从一开始就这么设计。
4. **最接近的结构范本 = NewPipe**（在线源 + 原生持队列 + 错时追加）：WINDOW_SIZE=1、距结尾 **30s** 触发、**2s 轮询**、**400ms debounce**，解析完成 append 进 ExoPlayer timeline；失败语义 playQueue.error() = **标记该条并推进**（与 core skipGuard/坏歌记忆同构）。它的预取窗口只有 30s，天然不撞 URL 过期——**这块它没有可抄代码**。
5. **签名直链过期只有个别项目解了**：Metrolist（expiresAtMillis + generation 防竞态）、SimpMusic（expiredTime + is403Url 预探测 + dataSpec.subrange 强制每个 chunk 重入 resolver）、Harmony-Music（错误回调里 playByIndex(newUrl) 重解析，注释原文就是 Workaround when 403）。**没有任何项目做「预解析 N 首 + 到期前刷新」→ 这块我们要自创。**
6. **反面教材（务必避开）**：InnerTune 缓存里存**相对 TTL** 却与 currentTimeMillis 比较 → 条件恒真 → URL 被无限期复用 → 曲末 403。→ 我们缓存项**必须存 expiresAtEpochMs**。
7. **失败处置只有 Metrolist 到位**：按 HTTP 码分级（403/410 = 过期）→ invalidate URL + delay(1s) + **校验 mediaId/index/position/playWhenReady 未变才重试**（防陈旧重试）+ 每曲 3 次上限 → 超限才标失败并按偏好跳/停；无网 waitOnNetworkError()。这就是我们 skipGuard 的原生侧对应物。
8. **Flutter 系的代价实证（= C′ 的现实版）**：namida **直接 fork 了两个插件**（just_audio、audio_service），真实 issue #838（后台播放提前 30s~1min 被切歌，已关）、#974（后台耗电）；Harmony-Music 把曲末推进写在 **Dart positionStream**（= #405 同型），README 自述要引导用户开「忽略电池优化」。

### 其它可直接写进 ADR 的共识

- 宿主统一用 **MediaLibraryService**（不是裸 MediaSessionService），单 service 挂 3 个 action + foregroundServiceType=mediaPlayback + FOREGROUND_SERVICE_MEDIA_PLAYBACK；通知 6/8 用 DefaultMediaNotificationProvider + setSmallIcon。
- 手写 MediaStyle 的 setShowActionsInCompactView 是 **action 下标硬编码**，必须与 addAction 顺序绑定（Retro (1,2,3)、VLC intArrayOf(1,2,3) 或 (0,2,4)、NewPipe 在 Android 13+ 干脆不设 compact）。
- **ForwardingPlayer**（AntennaPod 用）是「把策略下沉原生 + 保留 media3 默认通知/车机行为」的最省力入口：裁剪 availableCommands + 拦截 play/next。
- 进程死恢复：只有 AntennaPod 完整实现 onPlaybackResumption（注释写明**返回空会崩**）；其余走「队列序列化 + 周期落盘」，SimpMusic 的 onTrimMemory 落盘进度比纯定时器更抗 OEM 杀。
- onTaskRemoved 分歧最大：uamp 停播 / InnerTune stopSelf / Metrolist 默认保活（可配）/ AntennaPod 不重写（默认保活）/ **SimpMusic release + exitProcess(0) —— RN 宿主同进程，照抄会连 JS 上下文一起销毁，必须避开**。
- 反例：Jellyfin-androidtv 手写 MediaStyle + notify 但**没有 startForeground** → 自己发通知 ≠ 进入前台。

## 第一部分 · Media3 系（uamp/Metrolist/Auxio/SimpMusic/InnerTune/ViMusic/AntennaPod/Jellyfin）


> 调研对象：使用 `androidx.media3` 的 `MediaSessionService` / `MediaLibraryService` 的知名开源 Android 音乐播放器与流媒体客户端。
> 目的：为 MPlayer 移动端「原生持队列 + 原生推进」重构（候选 C：自写 Kotlin 模块；候选 C′：fork/patch expo-audio）提供可抄的结构与必须避开的坑。
> 证据口径：全部来自 commit-pinned 源码（下列 SHA 为撰写时抓取的各仓库分支 HEAD 提交），行号与所引 blob 一致。

## TL;DR

1. **队列所有权**：Metrolist / InnerTune / SimpMusic / ViMusic 都把「歌单序列」表示为原生 `androidx.media3.common.MediaItem` 列表直接灌进 ExoPlayer 的播放列表，**推进完全由原生 ExoPlayer 负责**；JS/UI 侧只做「一次性灌 + 分页补页」，从不逐曲驱动。
2. **这些项目不在 MediaItem 里放 URL**：`MediaItem.mediaId` 只放歌曲 id/元数据，真正的播放地址在 `ResolvingDataSource.resolveDataSpec()` **读取时才解析**（Metrolist、InnerTune、ViMusic、SimpMusic、AntennaPod 全走这条路）。→ 对第 3 问的直接结论：主流答案不是「提前 setMediaItems 好 URL」，而是 **resolveOnDataSpec**（比 resolveOnTransition 更细的粒度）。
3. **只有 Metrolist 把「签名直链会过期」当一等公民**：`StreamUrlCache` 带 TTL + generation 防竞态；SimpMusic 用 `expiredTime > now()` + 403 探测 + 每 chunk `subrange()` 强制重解析；InnerTune 的 TTL 判断写反了（恒真），是可引用的反面教材。
4. **会话宿主几乎统一是 `MediaLibraryService`**（不是 `MediaSessionService`），manifest 里一个 `<service>` 同时挂 `MediaSessionService` / `MediaLibraryService` / `MediaBrowserService` 三个 action，配 `foregroundServiceType="mediaPlayback"` + `FOREGROUND_SERVICE_MEDIA_PLAYBACK`。
5. **通知**：绝大多数直接用 media3 的 `DefaultMediaNotificationProvider` 再 `setSmallIcon(...)`，不自己写 MediaStyle（Metrolist 只包了一层 provider 来截获通知对象，Auxio / Jellyfin-AndroidTV 是仅有的自绘 `MediaStyle` 样本）。
6. **`onTaskRemoved` 分歧最大**：uamp 停止播放；InnerTune 直接 `stopSelf()`；Metrolist 按偏好走 `pauseAllPlayersAndStopSelf()`；SimpMusic 释放后 `exitProcess(0)`；AntennaPod 不重写（继承 media3 默认，滑动清任务后仍保活）。
7. **进程被杀恢复**：AntennaPod 用 `onPlaybackResumption` 从 DB 捞当前曲；Metrolist / InnerTune / SimpMusic 用「本地文件序列化整个队列 + onCreate 还原 + 周期性落盘」；uamp 只存最近一首；Jellyfin 交给**服务端**保存的 position。
8. **给 C/C′ 的三条**：抄「media3 播放列表当唯一队列 + DataSource 层即时解析 + 带 TTL 的 URL 缓存 + `onPlayerError` 分级重试（Metrolist 每曲 3 次上限）」；避开「在 JS 侧维护 playlist 或推进」「用它进程 Java 对象传队列（应走 media3 SessionCommand + Bundle）」「自己画通知却忘了 `startForeground`」。

## TL;DR

1. **这 8 个实现没有一个只用"一个 Service"就够了**：Retro / VLC / NewPipe / AntennaPod / Transistor / UAMP 全部是 `MediaBrowserServiceCompat` + 自建 `MediaSessionCompat`（VLC/NewPipe/Retro 还外挂 MediaSessionConnector 或等价回调）。C 用 `MediaSessionService` 能一步跨过这整套胶水，这是 media3 唯一无可替代的红利。
2. **队列所有权分两派**：(a) UAMP/AntennaPod 把整条 playlist 交给播放器（`setMediaItems(list, index, posMs)` / `MediaWrapperList`），曲末由播放器自己推进；(b) Retro/NewPipe/Transistor 只在播放器里放"当前这一首"，曲末事件回到 Kotlin/Java 再塞下一首。**在线源做不到 (a)**，因为 URL 要现解析——(b) 是我们 C′ 必然走到的位置。
3. **"在线源"的曲末无缝没有一个靠播放器原生 playlist 实现**（UAMP/AntennaPod 那种"整条列表交给播放器"只在 URL 已知且长期有效时成立）。最值得抄的是 NewPipe 的 `MediaSourceManager`：`WINDOW_SIZE = 1`（前后各预取 1 首）+ 距结尾 30s 起每 2s 触发一次加载 + `debounce(400ms)` 去抖 + 异步解析完成后 append 进 ExoPlayer timeline。
4. **签名 URL 过期只能"错了解析重来"**：Harmony-Music 在播放错误回调里 `customAction("playByIndex", {index, newUrl:true})` 重取直链（代码注释直接写 "Workaround when 403 error encountered"）。**没有任何一个项目做"预解析 N 首 + 到期前刷新"**——这是我们要自创的部分。
5. **手写 MediaStyle 时 compact 槽位是 action 下标的硬编码**，必须和 `addAction` 顺序严格绑定：Retro `setShowActionsInCompactView(1,2,3)`、VLC `intArrayOf(1,2,3)` 或 `intArrayOf(0,2,4)`、NewPipe/AntennaPod 按用户设置动态算下标。compact 错位是这类代码最高频的坑。
6. **生命周期共识**：`START_NOT_STICKY`（Retro/VLC/NewPipe/AntennaPod），只有 Transistor 用 `START_STICKY_COMPATIBILITY`；`onTaskRemoved` 三种态度——什么都不做（Transistor 里注释掉、Retro 根本没有）、停播（UAMP）、直接卸载进程（NewPipe `Runtime.getRuntime().halt(0)`）。
7. **唯一稳的恢复路径是数据库**：Retro 用 Room `MusicPlaybackQueueStore` + SharedPreferences 存位置；VLC 用 MediaDatabase + 位置；NewPipe 用 `PlayQueue.setRecovery(index, positionMs)`；UAMP 只有 `PersistentStorage` 存"最近一首"。
8. **Flutter 系的代价已经写在代码里**：namida 直接 fork 了两个插件（`MSOB7YY/just_audio` ref `video`、`MSOB7YY/audio_service` ref `minor`）——这就是 C′ 的现实版本：你 fork 的插件越深，越要自己维护它的 Android 侧；Harmony 的曲末推进写在 Dart 的 `positionStream` 里，正是我们 #405 的同型 bug，它自己的 #838 就是"后台被提前切歌"。

5. **服务生命周期**：全部返回 **START_NOT_STICKY**（[#L476](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/core/src/main/java/de/danoeh/antennapod/core/service/playback/PlaybackService.java#L476), [#L495](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/core/src/main/java/de/danoeh/antennapod/core/service/playback/PlaybackService.java#L495), [#L524](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/core/src/main/java/de/danoeh/antennapod/core/service/playback/PlaybackService.java#L524)）；**前台状态被抽成 `PlaybackServiceStateManager`**（onCreate 里建，[#L209](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/core/src/main/java/de/danoeh/antennapod/core/service/playback/PlaybackService.java#L209)），start/stop 都是 `stateManager.startForeground(...)` / `stateManager.stopForeground(!UserPreferences.isPersistNotify())`（[#L466](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/core/src/main/java/de/danoeh/antennapod/core/service/playback/PlaybackService.java#L466), [#L295](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/core/src/main/java/de/danoeh/antennapod/core/service/playback/PlaybackService.java#L295)）——**"前台状态机单独一个类"是这 8 个仓库里最干净的一处设计**。**用 WifiLock 而不是 WakeLock**（`WifiManager.WIFI_MODE_FULL`，[PlaybackServiceMediaPlayer.java#L275-L290](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/playback/base/src/main/java/de/danoeh/antennapod/playback/base/PlaybackServiceMediaPlayer.java#L275-L290)）。
6. **进程被杀后恢复**：**位置级恢复**，每次状态变化都 `saveCurrentPosition(true, null, Playable.INVALID_TIME)`（[PlaybackService.java#L753](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/core/src/main/java/de/danoeh/antennapod/core/service/playback/PlaybackService.java#L753), [#L801](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/core/src/main/java/de/danoeh/antennapod/core/service/playback/PlaybackService.java#L801), [#L871](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/core/src/main/java/de/danoeh/antennapod/core/service/playback/PlaybackService.java#L871)），由 `PlaybackServiceTaskManager` 定时落库；恢复时"从数据库取这一集 + 位置"，不是"恢复整条队列"。
7. **失败处置**：抽象契约直接把语义写进 javadoc：**出错跳下一集 = `endPlayback(false, false, true, true)`**（[PlaybackServiceMediaPlayer.java#L246](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/playback/base/src/main/java/de/danoeh/antennapod/playback/base/PlaybackServiceMediaPlayer.java#L246)）——**"错误＝跳过"是它的第一公民语义**，无重试计数。
8. **版本与依赖**：compileSdk/targetSdk **31**、**minSdk 21**（[common.gradle@3.0.2#L2-L6](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/common.gradle#L2-L6)）；`androidx.media:media`（[app/build.gradle@3.0.2](https://github.com/AntennaPod/AntennaPod/blob/b063f0508f6e6439509f22769374c57f77cb499f/app/build.gradle)）；**develop 现状**：media3 **1.10.0** + Kotlin 2.3.20（[libs.versions.toml#L3-L4](https://github.com/AntennaPod/AntennaPod/blob/6f080458603af15f4acc20e09811884c1fe80dc9/gradle/libs.versions.toml#L3-L4)）。
9. **对 C/C′ 的启示**：可抄 **`PlaybackServiceStateManager`（前台状态机独类）+ 通知 builder 独文件 + MediaPlayer 包装独模块** 的三段切分——C 的 Kotlin 模块应当照这个切（否则就是 VLC 那种 isForeground 布尔满天飞）；可抄"错误＝跳过"作为一等语义。必须避开：**"移动网络起播前先弹通知等用户确认"**，我们的场景必须无交互自动起播。
