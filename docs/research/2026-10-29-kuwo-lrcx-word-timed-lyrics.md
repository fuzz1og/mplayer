# 酷我 lrcx 逐字歌词格式（#722 取证）

> 调研日期: 2026-10-29
> 目标: 判定「行内 `<a,b>` 逐字标签」的时间轴语义能否可靠还原，用于 #722（桌面歌词把标签当正文渲染）
> 方法: 走真实取词链路抓原文（core `musicApi.getLyrics` → 酷我 `newlyric.kuwo.cn/newlyric.lrc` 带 `lrcx=1`）+ 两处独立 OSS 实现对照 + 用真实样本自证（末字终点应与下一行时间戳重合）

## 0. TL;DR

1. 这套格式是**酷我 lrcx**：酷我取词 URL 恒带 `lrcx=1`（`packages/core/src/api/kuwoDirect.ts:145-151`），响应解出来就是它。**不是** KRC / QRC / YRC / LYS——那几套的行内标签是 `[s,d,0]` / `(s,d,0)` / `(s,d)`，只有酷我用两值尖括号，且第二列可以为负。
2. 语义：文件头 `[kuwo:NNN]` 的 NNN 按**八进制**读出 v，拆成两位系数 `k1 = ⌊v/10⌋`、`k2 = v mod 10`；对每个词，`起点 = |a+b| / (2·k1)`、`时长 = |a−b| / (2·k2)`，单位毫秒、相对行首。等价于编码端 `a = k1·起点 + k2·时长`、`b = k1·起点 − k2·时长`——首词起点为 0，于是 `a = k2·时长`、`b = −k2·时长`，这正是截图里第二列为负值的来源。
3. 还原可靠（可做逐字高亮）：6 首真实样本的逐字区间**单调不减**，且**末字终点 ≤ 下一行时间戳**；起风了/旺仔小乔 68 个逐字行里 36 行的末字终点与下一行时间戳**精确相等**（毫秒级），其余留间隙。

## 1. 真实原文（酷我 lrcx）

同一首歌的 `lrcx=1` 响应解出来（节选，完整样本见 `src/renderer/__tests__/fixtures/kuwo-lrcx-075.txt` 与 `kuwo-lrcx-041.txt`）：

```
[kuwo:075]
[00:00.000]<901,-901>起<5726,5086>风<7621,7031>了 <9397,8795>- <11203,10601>旺<13007,12409>仔<14804,14200>小<16591,16037>乔
[00:02.996]<299,-299>词：<2091,1497>米<3878,3274>果
```

issue #722 截图里那两行是同一个编码（首词二列恒等于首词一列的相反数、二列先负后正），只是缺少文件头所以无法反算系数。

## 2. 公式与自证

`[kuwo:075]` → 八进制 075 = 十进制 61 → k1 = 6、k2 = 1。把上面第一行代进公式：

| 词 | a | b | 起点 (ms) = |a+b|/12 | 时长 (ms) = |a−b|/2 |
|---|---|---|---|---|
| 起 | 901 | -901 | 0 | 901 |
| 风 | 5726 | 5086 | 901 | 320 |
| 了 | 7621 | 7031 | 1221 | 295 |
| … | | | | |
| 乔 | 16591 | 16037 | 2719 | 277 |

最后一位「乔」的终点 2719+277 = **2996ms**，与下一行时间戳 `[00:02.996]` **逐毫秒相等**；整行 901→2996 无空洞也无越界。这是公式正确的最硬一条自证（猜错系数时不可能对齐）。

同一首歌的统计（脚本口径：逐行算起点/终点，比较末字终点与下一行时间戳）：

| 样本 | 文件头 | 逐字行数 | 起点单调不减 | 末字终点 ≤ 下一行 | 精确相等 |
|---|---|---|---|---|---|
| 起风了 / 旺仔小乔 | `[kuwo:075]` (6,1) | 68 | 68/68 | 67/67 | 36 |
| 后来 / 刘若英 | `[kuwo:142]` (9,8) | 44 | 44/44 | 43/43 | 0（末字 2520ms vs 下一行 2528ms） |
| 孤勇者 / 白慕寒 | `[kuwo:041]` (3,3) | 53 | 53/53 | 52/52 | 0 |

## 3. 独立实现对照（两处可复核出处）

1. **Yudaotor/lyrimuse（Go）** `lyrimuse-engine/kuwolrcx.go`，原文注释：
   > 「每个 `<a,b>` 不是明文时间：`[kuwo:NNN]` 的 NNN 按八进制读出 v，k1 = v/10、k2 = v%10，词起点 = |a+b| / (2·k1)、词长 = |a−b| / (2·k2)，都是相对行首的毫秒」
   > 「词都在标记**之后**」
   
   https://github.com/Yudaotor/lyrimuse/blob/main/lyrimuse-engine/kuwolrcx.go （`kuwoLrcxCoefficients` / `kuwoLrcxWordTiming`）
2. **0Hyacinth0/Notch-Triage（Swift）** `NotchTriage/KuwoLRCX.swift`：同一组系数与同一公式（`relativeStart = |a+b| / (2·first·1000)`），并同样在「后词起点早于前词终点」时截断前一个词；`<0,0>` 整行（译文/占位行）整行丢弃。

   https://github.com/0Hyacinth0/Notch-Triage/blob/main/NotchTriage/KuwoLRCX.swift

两处实现独立、语言不同、都从酷我客户端行为反推，公式与本文实测一致——所以这不是单点推测。

## 4. 边界

- **必须要有 `[kuwo:NNN]` 文件头**才能反算系数。缺头（或系数出现 0）时只剥离标签、保留行级时间，不给逐字轨道（`parseLRC` 就这么做）。
- 整行标签都是 `<0,0>` 的是**译文/占位行**（挂在下一句原文的时间戳上）：只保留正文，不产出逐字轨道，避免 0 时长的词。
- 逐字轨道的行数/文案与行级完全一致（标签只存在于行内），因此行级渲染与既有测试口径不变。
- 本仓其他源**不产出**这套标签（2026-10-29 实测）：QQ fcg、咪咕、千千、酷狗（`fmt=lrc`）都是纯 LRC；网易 `lrc.lyric` 是纯 LRC；汽水的结构化 `sentences[].words` 早已由 `sodaSentencesToLrc` 归一成纯 LRC。KRC（酷狗，base64+zlib 二进制 `krc18`）与 QQ QRC 不在本仓取词链路里。
- 酷我同一首歌可能给多份词（AI 生成 / 用户上传），文件头系数按文件走，不能跨文件复用。
