# Agent-first / AFK 开源项目的 PR·Issue 模板与贡献流程调研（一手来源）

> 调研日期：2026-09-30 · 类型：调研 · 目的：为 MPlayer `.github/` 的 PR 模板（现为「变更内容 / 关联 issue / 验证 / 备注」+ 8 项验证清单）与 Issue Forms 的改版提供外部参照。背景抱怨：agent 写的 PR 正文 2.6k–3.8k 字符 / 54–81 行，啰嗦、失焦、不是平实语言。
> 依据：**仅一手来源** —— 各仓库自身文件（`raw.githubusercontent.com` 取原文，`gh api` 取文件树）。引用为**逐字短引文**（英文原文），每处附来源 URL。**凡未能核实的条目一律写「未找到」，不做推测。**
> 范围：agent-first / AFK 生态（mattpocock/skills、humanlayer、openai/codex、google-gemini/gemini-cli、sst/opencode、cline/cline、RooCodeInc/Roo-Code、Aider-AI/aider、block/goose），外加调研中额外发现的 All-Hands-AI/OpenHands；Kubernetes/Rust/Node/React 等由另一路调研覆盖，本文不重复。
> 校验方式：每条 URL 均为本次抓取的实际地址；引用行数均 <15 行。
> 状态（2026-10-01）：**已落地** —— `.github/` 的 PR 模板已改用 `pr` skill 的三段式（Summary / Evidence / Merge Danger），§12「与 MPlayer 现状的直接对照」被该改动取代；§1–§11 的外部调研与逐字引文仍作参考（本文属存档类，定稿即不再改）。

---

## 0. 结论先行（供改造决策用）

1. **「短」不是靠删检查项，而是靠把检查项做成门禁。** OpenHands 的 PR 模板只有 Why / Summary（1–3 条 bullet）/ Issue Number / How to Test / Video-Screenshots / Type / Notes 七段，但把「证据」写进 issue 模板的字段描述里（原文："Required for the `ready-for-dev` label"）。goose 同类：正文里只有 `Fixes: #ISSUE_ID` + 一段 IMPORTANT，其余靠 issue 状态。
2. **反差最大的一条是「反 AI 倾倒」明文**：opencode 在 PR 模板里直接写「大的明显 AI 生成的描述 → 可能被忽略或关闭」；goose 在 CONTRIBUTING 里写「不用告诉我们你用了 AI……我们会关闭明显跳过了自查的 vibe coding 提交」；mattpocock/skills 要求 triage 的每条评论必须带 AI 披露前缀。**MPlayer 抱怨的「啰嗦、不是平实语言」在这个生态里已有成文对策，可直接借用措辞。**
3. **三个项目用「状态标签」而非模板长度来约束 agent**：mattpocock/skills 的 `ready-for-agent`（AFK agent 可做）、OpenHands 的 `ready-for-dev`（含验收标准才给）、goose 的看板 `Ready`（不在 Ready 的 PR 直接关）。
4. **模板注释是「教怎么写」的位置**：cline 的 HTML 注释直接说明「小的 PR 描述可以很少，大改动才需要解释，能引用 issue 就别重复」；gemini-cli 的注释说明每条该写什么。MPlayer 的 8 项清单缺的正是这种「什么算够、什么算过度」的边界。
5. **机器人只查「链接与标签」，不查「正文写得像不像人」**：gemini-cli 的 `pr-triage.sh` 只做「无关联 issue → 打 `status/need-issue`」；opencode 的 `triage.yml` 只自动分配负责人；codex 只有一份 triage prompt 文件。**没有任何一个项目用 CI 检查正文长度或语气。**

## 1. mattpocock/skills（AFK 术语与 `ready-for-agent` 的源头）

仓库：https://github.com/mattpocock/skills （默认分支 `main`）

### 1.1 PR 模板 / Issue 模板

**未找到。** 该仓库的文件树里 `.github/` 下只有 `.github/workflows/release.yml`（`gh api repos/mattpocock/skills/git/trees/main?recursive=1`），没有 `PULL_REQUEST_TEMPLATE`、也没有 `ISSUE_TEMPLATE/`。它的「模板」不是 GitHub 模板，而是**写进 issue 评论里的 Agent Brief**（见 1.3）。

### 1.2 状态机与标签（AFK 措辞的出处）

`skills/engineering/triage/SKILL.md`（[链接](https://github.com/mattpocock/skills/blob/main/skills/engineering/triage/SKILL.md)）：

> Two **category** roles: `bug` / `enhancement`
> Five **state** roles: `needs-triage` / `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`

其中 `ready-for-agent` 的定义原文即 AFK：

> `ready-for-agent`: fully specified, ready for an AFK agent

冲突处理规则也在同一文件：

> Every triaged issue should carry exactly one category role and one state role. If state roles conflict, flag it and ask the maintainer before doing anything else.

标签名到实际 label 字符串的映射在 `skills/engineering/setup-matt-pocock-skills/triage-labels.md`（[链接](https://github.com/mattpocock/skills/blob/main/skills/engineering/setup-matt-pocock-skills/triage-labels.md)），该文件明确「canonical role ≠ 实际 label」：

> The skills speak in terms of five canonical triage roles. This file maps those roles to the actual label strings used in this repo's issue tracker.

### 1.3 Agent Brief（agent 领取工作时的「契约」）

`skills/engineering/triage/AGENT-BRIEF.md`（[链接](https://github.com/mattpocock/skills/blob/main/skills/engineering/triage/AGENT-BRIEF.md)）给出固定模板与两条写作原则，**直接针对「agent 写出来啰嗦」的根因**：

> The brief states **what the agent should do** … Write the brief so it stays useful even as files are renamed, moved, or refactored.
> - **Don't** reference file paths: they go stale
> - **Don't** reference line numbers

模板结构（**7 段**，每段都有硬约束）：

> ```markdown
> ## Agent Brief
> **Category:** bug / enhancement
> **Summary:** one-line description of what needs to happen
> **Current behavior:** …
> **Desired behavior:** …
> **Key interfaces:** …
> **Acceptance criteria:** - [ ] Specific, testable criterion 1
> **Out of scope:** - Thing that should NOT be changed
> ```

并且对「行为 vs 流程」给了正反例：

> - **Good:** "The `SkillConfig` type should accept an optional `schedule` field of type `CronExpression`"
> - **Bad:** "Open src/types/skill.ts and add a schedule field on line 42"

### 1.4 AI 来源披露（强制）

`SKILL.md` 顶部即规定 triage 期间产生的每条评论必须带披露前缀：

> Every comment or issue posted to the issue tracker during triage **must** start with this disclaimer:
> ```
> > *This was generated by AI during triage.*
> ```

### 1.5 机器人 / CI 检查正文

**未找到。** 该仓库没有 workflow 检查 issue/PR 正文（`.github/workflows/` 仅 release）。`docs/engineering/triage.md`（[链接](https://github.com/mattpocock/skills/blob/main/docs/engineering/triage.md)）明确 triage 是**人工触发、且只处理别人创建的条目**：

> The rule is flat: `/triage` is only for incoming issues, not for issues you created yourself.
> The second thing that separates it from labelling by hand: it recommends and waits.

### 1.6 约定的传播（旁证）

GitHub 代码搜索 `"AFK agent"`（`gh api -X GET search/code`）返回大量**下游仓库逐字复制该约定**的文件，例如 `cipherstash/stack` 的 `docs/agents/triage-labels.md`（[链接](https://github.com/cipherstash/stack/blob/main/docs/agents/triage-labels.md)）：

> | `ready-for-agent` | `ready-for-agent` | Fully specified and ready for an AFK agent |

说明「`ready-for-agent` = AFK 可做」已成为跨仓库词汇，而非单仓库私例。

## 2. humanlayer（humanlayer/humanlayer + 其 AFK 写作）

仓库：https://github.com/humanlayer/humanlayer （默认分支 `main`）

### 2.1 PR 模板：6 个标题、1 个勾选框

`.github/PULL_REQUEST_TEMPLATE.md`（[链接](https://github.com/humanlayer/humanlayer/blob/main/.github/PULL_REQUEST_TEMPLATE.md)），**全文结构**（这是本次调研中最短的一份 PR 模板）：

> ```markdown
> ## What problem(s) was I solving?
> ## What user-facing changes did I ship?
> ## How I implemented it
> ## How to verify it
> - [ ] I have ensured `make check test` passes
> ## Description for the changelog
> ## A picture of a cute animal (not mandatory but encouraged)
> ```

要点：**无「变更内容/备注」式分类小节**；用第一人称问句（"What problem(s) **was I** solving?"）把正文锚定在「问题与验证」两件事上；验证只有 1 个勾选框；留了一个刻意轻松的收尾项。

### 2.2 Issue 模板：3 个 Markdown 模板（非 Forms）

| 文件 | 触发标签 | 必填内容（原文要点） |
|---|---|---|
| `.github/ISSUE_TEMPLATE/bug_report.md`（[链接](https://github.com/humanlayer/humanlayer/blob/main/.github/ISSUE_TEMPLATE/bug_report.md)） | `bug` | Current Behavior / Expected Behavior / Steps to Reproduce（1.2.3.）/ Context（Component、Version、OS、Node/Go version、**Nightly build version**、**Claude code version**） |
| `.github/ISSUE_TEMPLATE/feature_request.md`（[链接](https://github.com/humanlayer/humanlayer/blob/main/.github/ISSUE_TEMPLATE/feature_request.md)） | `enhancement` | Problem / Use Case、Proposed Solution、Alternative Solutions Considered |
| `.github/ISSUE_TEMPLATE/feedback.md`（[链接](https://github.com/humanlayer/humanlayer/blob/main/.github/ISSUE_TEMPLATE/feedback.md)） | `feedback` | Feedback、Context（Component/Area） |

模板正文用 HTML 注释给出「写什么」的提示，例如 bug 模板：

> `## Current Behavior / Issue`
> `<!-- Describe what is currently happening that shouldn't be happening -->`

bug 与 feature 模板结尾都带一个趣味项（feature 的原文）：

> `## Photo of a cute animal`
> `<!-- please include a photo of a cute animal -->`

### 2.3 CONTRIBUTING.md：PR 正文由 agent 命令生成

`CONTRIBUTING.md`（[链接](https://github.com/humanlayer/humanlayer/blob/main/CONTRIBUTING.md)）的 "Commands cheat sheet" 把「写 PR 正文」列为 agent 工作流的一步：

> ```
> 1. `/research_codebase`
> 2. `/create_plan`
> 3. `/implement_plan`
> 4. `/commit`
> 5. `gh pr create --fill`
> 6. `/describe_pr`
> ```

即：**PR 正文由 `/describe_pr` 从 plan 推导**，而不是让 agent 自由发挥（这正是「正文膨胀」的结构性对策）。

### 2.4 AGENTS.md / CLAUDE.md

根 `CLAUDE.md`（[链接](https://github.com/humanlayer/humanlayer/blob/main/CLAUDE.md)）是**代码库导航与开发约定**（monorepo 结构、`make check-test`、TODO(0)…TODO(4) 优先级注解系统），**没有**任何关于 issue/PR 正文写法的规定。

### 2.5 AFK 措辞

**未找到。** 核查范围与结果：
- 仓库代码搜索 `AFK repo:humanlayer/humanlayer` 与 `AFK repo:humanlayer/12-factor-agents` 仅命中 lockfile（`bun.lock`/`package-lock.json`），无文档命中；
- 官方博客索引 https://www.humanlayer.com/blog 与文章 https://www.humanlayer.com/blog/advanced-context-engineering 抓取后匹配 `AFK` = 0 次、`away from keyboard` = 0 次。

其 ACE 文章讲的是另一套词汇（context engineering / intentional compaction），不是 AFK 标签体系。

## 3. openai/codex

仓库：https://github.com/openai/codex （默认分支 `main`）

### 3.1 PR 模板

**未找到。** 原因是政策性的 —— `docs/contributing.md`（[链接](https://github.com/openai/codex/blob/main/docs/contributing.md)）原文：

> **We do not accept external code contributions or pull requests.**

> Community expertise is most valuable when shared through detailed bug reports, reproduction steps, logs, root-cause analysis, and design discussions in issues. … implementation is comparatively straightforward with the help of Codex itself.

所以它的「模板」全部投在 **issue 侧**，且要求把「根因分析」也写进 issue：

> - Root-cause analysis, technical observations, or potential approaches to a fix, if available.

### 3.2 Issue Forms：6 个按组件拆分的 Forms

文件：`.github/ISSUE_TEMPLATE/` 下 `1-codex-app.yml`、`2-extension.yml`、`3-cli.yml`、`4-bug-report.yml`、`5-feature-request.yml`、`6-docs-issue.yml`。前 4 个是 bug 类，**结构几乎相同：3 个必填 textarea + 若干 input**。

`4-bug-report.yml`（[链接](https://github.com/openai/codex/blob/main/.github/ISSUE_TEMPLATE/4-bug-report.yml)）必填字段：

> id: actual → "What issue are you seeing?" （`required: true`）
> id: steps → "What steps can reproduce the bug?" （`required: true`）
> id: expected → "What is the expected behavior?" （无 required）

正文里的三条写作纪律（可逐字借用到 MPlayer）：

> Please include the full error messages and prompts with PII redacted. If possible, please provide text instead of a screenshot.

> Before submitting a new issue, please search for existing issues to see if your issue has already been reported.
> If it has, please add a 👍 reaction (no need to leave a comment) to the existing issue instead of creating a new one.

`1-codex-app.yml`（[链接](https://github.com/openai/codex/blob/main/.github/ISSUE_TEMPLATE/1-codex-app.yml)）额外要求**版本与平台命令**，并给出可复制指令：

> For macOS and Linux: copy the output of `uname -mprs`

`5-feature-request.yml` 用 markdown block 声明「不保证接受」：

> The Codex team will try to balance the varying needs of the community when prioritizing or rejecting new features. Not all features will be accepted.

### 3.3 Labels

Forms front matter 里直接指定初标签：`1-codex-app.yml` → `app`；`4-bug-report.yml` → `bug`；`5-feature-request.yml` → `enhancement`；`6-docs-issue.yml` → `documentation`。仓库根有 `.github/CODEOWNERS`（[链接](https://github.com/openai/codex/blob/main/.github/CODEOWNERS)）。

### 3.4 机器人 / 自动化

存在 `.github/codex/labels/codex-triage.md`（[链接](https://github.com/openai/codex/blob/main/.github/codex/labels/codex-triage.md)），**全文只有 4 行**，是喂给自家 triage 自动化的 prompt，文件名与目录名（`codex/labels/`）表明它同时承担打标签职责：

> Troubleshoot whether the reported issue is valid.
> Provide a concise and respectful comment summarizing the findings.
> ### {CODEX_ACTION_ISSUE_TITLE}
> {CODEX_ACTION_ISSUE_BODY}

注意其唯一写作要求就是 **concise（简洁）**。

### 3.5 AGENTS.md

根 `AGENTS.md`（[链接](https://github.com/openai/codex/blob/main/AGENTS.md)）是 **Rust 代码规范**（crate 命名、clippy 规则、`/*param_name*/` 注释约定等），**不含** issue/PR 写作规范。其中一条与「别把验证成本推给 CI」相关：

> Most of the time, it is best to update the PR and let CI take responsibility for checking this (or run it asynchronously in the background after submitting the PR).

## 4. google-gemini/gemini-cli

仓库：https://github.com/google-gemini/gemini-cli （默认分支 `main`）

### 4.1 PR 模板：5 段，注释说明每段标准

`.github/pull_request_template.md`（[链接](https://github.com/google-gemini/gemini-cli/blob/main/.github/pull_request_template.md)）：

> ```markdown
> ## Summary
> <!-- Concisely describe what this PR changes and why. Focus on impact and urgency. -->
> ## Details
> <!-- Add any extra context and design decisions. Keep it brief but complete. -->
> ## Related Issues
> <!-- Use keywords to auto-close issues (Closes #123, Fixes #456). … -->
> ## How to Validate
> <!-- List exact steps for reviewers to validate the change. Include commands, expected results, and edge cases. -->
> ## Pre-Merge Checklist
> ```

清单本体 4 项（文档 / 测试 / breaking change / 平台验证），但**平台矩阵是嵌套的**（MacOS|Windows|Linux × npm run|npx|Docker[|Podman|Seatbelt]），属本次调研中唯一「清单比正文长」的例子 —— 与 MPlayer 的 8 项清单同型，可作反面参照。

### 4.2 Issue Forms

- `bug_report.yml`（[链接](https://github.com/google-gemini/gemini-cli/blob/main/.github/ISSUE_TEMPLATE/bug_report.yml)）：3 个必填（problem / expected / **Client information**），并**给出粘贴模板与隐私提示**：
  > Please paste the full text from the `/about` command run from Gemini CLI. … Note that this output contains your email address. Consider removing it before submitting.
- `feature_request.yml`（[链接](https://github.com/google-gemini/gemini-cli/blob/main/.github/ISSUE_TEMPLATE/feature_request.yml)）：**创建即打标签** —— `labels: ['status/need-triage']`，并声明 `type: 'Feature'`；必填 2 项（feature / rationale）。
- `website_issue.yml` 另有一份。

### 4.3 CONTRIBUTING.md：6 条 PR 规则（对 MPlayer 最可直接借用的一节）

`CONTRIBUTING.md`（[链接](https://github.com/google-gemini/gemini-cli/blob/main/CONTRIBUTING.md)）"### Pull request guidelines" 开头即设闸门：

> To help us review and merge your PRs quickly, please follow these guidelines.
> PRs that do not meet these standards may be closed.

1. **Link to an existing issue**（配自动关闭）：
   > If an issue for your change doesn't exist, we will automatically close your PR along with a comment reminding you to associate the PR with an issue.
2. **Keep it small and focused**：
   > - **Do:** Create a PR that fixes one specific bug or adds one specific feature.
   > - **Don't:** Bundle multiple unrelated changes (e.g., a bug fix, a new feature, and a refactor) into a single PR.
3. **Use draft PRs for work in progress**
4. **Ensure all checks pass**（`npm run preflight`）
5. **Update documentation**（用户可见变更必须改 `/docs`）
6. **Write clear commit messages and a good PR description**：
   > In the PR description, explain the "why" behind your changes and link to the relevant issue (e.g., `Fixes #123`).

另有**作者自查自动化审查**的要求：

> **Authors are strongly encouraged to run this script on their own PRs** immediately after creation.

### 4.4 Labels

- `help-wanted`（**仅 maintainer 可打**，且只有打了它的 issue 才能自领）：
  > Only maintainers should attempt to add the `help-wanted` label to an issue.
  > Please note that you can have a maximum of 3 issues assigned to you at any given time
- `🔒Maintainers only`（保留 issue）："we will not accept pull requests related to these issues."
- 状态类：`status/need-triage`（表单自动打）、`status/need-issue`（PR 机器人打）。
- area/priority 类标签由 PR 机器人从关联 issue 同步。

### 4.5 机器人 / CI 检查正文（本生态里最完整的一例）

| 文件 | 作用 |
|---|---|
| `.github/workflows/gemini-automated-issue-triage.yml`（[链接](https://github.com/google-gemini/gemini-cli/blob/main/.github/workflows/gemini-automated-issue-triage.yml)） | issue opened/reopened 触发 LLM triage；已带 `area/` 标签的跳过（`!contains(github.event.issue.labels.*.name, 'area/')`）；也支持 `@gemini-cli /triage` 评论触发（限 OWNER/MEMBER/COLLABORATOR） |
| `.github/scripts/pr-triage.sh`（[链接](https://github.com/google-gemini/gemini-cli/blob/main/.github/scripts/pr-triage.sh)） | 检查 PR 是否关联 issue：无 `ISSUE_NUMBER` 的非 draft PR → 打 `status/need-issue` 并留评论；有关联则把 issue 的 `(area|priority)/*`、`help wanted`、`🔒 maintainer only` 同步到 PR |
| `gemini-scheduled-issue-triage.yml` / `gemini-scheduled-pr-triage.yml` / `cleanup-triage-labels.cjs` / `backfill-need-triage.cjs` | 周期性 triage 与标签清理 |

**注意**：机器人只校验「有没有关联 issue」，不校验正文长度或语气。

### 4.6 GEMINI.md

`GEMINI.md`（[链接](https://github.com/google-gemini/gemini-cli/blob/main/GEMINI.md)）是**项目上下文与构建/测试命令**（`npm run preflight` 为最重检查，"only run this at the very end of a code implementation task"），**不含** issue/PR 正文规范。

## 5. sst/opencode（反 AI 倾倒措辞最直接）

仓库：https://github.com/sst/opencode （默认分支 **`dev`**，下列链接均为 `/blob/dev/`）

### 5.1 PR 模板（[链接](https://github.com/sst/opencode/blob/dev/.github/pull_request_template.md)）

**全文核心**：

> ```markdown
> ### Issue for this PR
> Closes #
> ### Type of change
> - [ ] Bug fix  - [ ] New feature  - [ ] Refactor / code improvement  - [ ] Documentation
> ### What does this PR do?
> Please provide a description of the issue, the changes you made to fix it, and why they work. …
> **If you paste a large clearly AI generated description here your PR may be IGNORED or CLOSED!**
> ### How did you verify your code works?
> ### Screenshots / recordings
> ### Checklist
> - [ ] I have tested my changes locally
> - [ ] I have not included unrelated changes in this PR
> _If you do not follow this template your PR will be automatically rejected._
> ```

三处可直接借用的措辞：
1. **对 AI 长文的正告**（加粗、全大写效果）；
2. **把「为什么你的改动是对的」写进要求**，并要求不懂就承认：
   > It is expected that you understand why your changes work and if you do not understand why at least say as much so a maintainer knows how much to value the PR.
3. **清单只有 2 项**（本地测过 + 无无关改动）。

> 注：模板末尾的「automatically rejected」在仓库里**未找到**对应的检查 workflow（`.github/workflows/` 只有 `triage.yml` 等针对 issue 的自动化），该句属模板声明而非已核实的 CI 行为。

### 11.10 大型改动的规模闸门（3 个项目）

- **gemini-cli**："We favor small, atomic PRs… Don't bundle multiple unrelated changes"
- **goose**："Don't open many pull requests in quick succession."
- **cline**：Pre-flight 清单第 1 项 "Changes are limited to a single feature, bugfix or chore (split larger changes into separate PRs)"

### 11.11 机器自动套模板的坑（1 个项目，但与本仓直接相关）

- **goose** AGENTS.md：`gh issue create` does not apply templates automatically.
  → 对本仓的含义：MPlayer 的 agent 用 `gh pr create` 时**不会自动套模板**，模板要求的结构必须写进 agent 指令或由模板文件本身可被 agent 读取（OpenHands 的做法是把 HUMAN/AGENT 分区放在模板文件里，agent 读取后照抄）。
