# 桌面端 UI 收口 v2 — macOS SwiftUI 全量视觉与交互统一（2026-10-28）

> 状态：设计已确认，待原型与实施。本版取代同日早稿；早稿中的固定数值、常驻复选框、按路由分配页面壳和 P0/P1 划分不再有效。
> 基线：feat/ui-redesign-1.9.0（PR #691）；父 issue：#678。
> 设计目标：macOS Apple Music / SwiftUI 桌面范式的高级简约；保留 Windows 自绘窗口按钮，不复制 macOS 交通灯。
> 既有决策：自建 UI 原语、全屏设置、选中态不用品牌蓝及严格 design-lint 的 ADR 继续有效。

## Problem Statement

桌面端当前的问题不是缺少一套颜色或圆角，而是信息层级、列表语义、导航所有权和桌面控件语法没有统一。资料库、设置和正在播放已出现新语言，推荐、发现、收藏、详情、队列与浮层仍分别沿用旧模式；即使把旧规格的 46px 行高、30px 封面和 6px 搜索框全部收齐，也仍可能只是一个浅色网页音乐客户端。

用户需要的是一个完整、安静、可读的桌面应用：歌曲列表不被常驻复选框和重复列占据，详情页没有双标题和双返回，设置文字与动作不被拉到宽窗口两端，暗色按钮与浮层保持正确层级，正在播放不会遮住窗口控制，查看队列不会丢失当前浏览上下文。

同时，现有实现还有不能被视觉改造掩盖的功能缺口：两个详情页的批量下载没有实际回调，最近播放缺少播放全部，列表与调用方对播放队列的职责不一致，全屏到设置的测试绕过了真实遮挡路径。新规格必须同时约束视觉、行为与验收证据。

## Solution

以“全量视觉收口 + macOS 桌面基准”重做本轮 UI，而不是继续按早稿逐页补类名：

- 用平面歌曲列表承载媒体内容，用分组列表承载设置和表单。
- 用一套标题栏拥有全局返回、搜索、设置、帮助和窗口控制；详情页只保留内容 hero。
- 用共享歌曲行协议统一排版、密度、操作和虚拟测量，同时允许列与封面按内容场景变化。
- 用按需选择模式替代常驻复选框，保留全部批量能力。
- 用统一的桌面按钮、分段控件、菜单和 Dialog 取代胶囊、浮起卡片和多套浮层语言。
- 用真实的滚动穿透或有意实色表达 chrome 层级，不把 blur 数值当作材质完成度。
- 用右侧非模态队列面板保留浏览上下文；正在播放保留双列签名布局但不得覆盖窗口控制。
- 用全路由、双主题、真实 Electron 的行为与几何证据作为交付门槛。

实施先经过七个代表性原型和两条垂直切片，再推广到全部页面。保留当前 worktree 中有效的共享列表与 chrome 成果，不回退、不清理未跟踪成果，也不把早稿数值当成验收目标。

## User Stories

1. 作为桌面用户，我希望所有产品页面使用同一套信息层级和控件语言，以便在不同页面间切换时不必重新理解界面。
2. 作为桌面用户，我希望一级页面具有一致的标题、说明、操作位置和留白，以便快速识别当前位置与可用动作。
3. 作为桌面用户，我希望侧栏用「资料库」分组承载我喜欢的音乐、最近播放、我的歌单与本地，以便理解这些内容属于同一集合，而不必进入一个混装的聚合页。
4. 作为桌面用户，我希望每个内容库页面用分段控件在歌曲、专辑、歌手三个视角间切换，以便同一批数据换个看法，而不用分辨「过滤维度」与「内容库」的区别。
5. 作为桌面用户，我希望“我喜欢的音乐”在侧栏、标题、空态和可访问名称中一致，以便不会与动作“收藏”混淆。
6. 作为桌面用户，我希望最近播放可以一键播放全部，以便继续按历史顺序听歌。
7. 作为桌面用户，我希望清空历史不是页面最突出的动作，以便不会误删记录。
8. 作为桌面用户，我希望歌曲列表直接落在内容表面，以便减少无意义的大卡片和视觉边框。
9. 作为桌面用户，我希望歌曲标题粗细适中、歌手与专辑清晰可读，以便长时间浏览列表而不疲劳。
10. 作为桌面用户，我希望专辑详情不重复显示每一行的相同专辑名，以便把空间留给有效信息。
11. 作为桌面用户，我希望队列优先呈现当前顺序、歌曲和时长，以便快速理解接下来播放什么。
12. 作为桌面用户，我希望搜索、收藏和歌单能按场景保留专辑、来源或封面，以便获得足够辨识信息。
13. 作为桌面用户，我希望默认列表没有常驻复选框，以便界面保持安静。
14. 作为桌面用户，我希望能显式进入选择模式并完成批量下载、加入歌单或移除，以便批量管理歌曲。
15. 作为桌面用户，我希望退出选择模式后恢复普通列表，以便继续浏览。
16. 作为桌面用户，我希望分组搜索、普通列表和拖拽列表具有一致的歌曲行外观，以便不觉得它们来自不同应用。
17. 作为桌面用户，我希望拖拽、过滤、无限滚动、空态和骨架屏在改造后仍然可用，以便不损失已有能力。
18. 作为桌面用户，我希望点播任何列表中的歌曲都建立正确的播放队列，以便上一首、下一首和随机推进符合当前上下文。
19. 作为桌面用户，我希望专辑与发现歌单的批量下载真正开始下载，以便不会遇到可点击但无反应的按钮。
20. 作为桌面用户，我希望标题栏不显示品牌块和多余提示，以便把空间留给导航与搜索。
21. 作为桌面用户，我希望全局搜索保持居中、6px 圆角且没有 Ctrl K 提示或绑定，以便随时跨页搜索。
22. 作为桌面用户，我希望搜索来源菜单不被内容遮挡且可用键盘操作，以便可靠切换搜索范围。
23. 作为桌面用户，我希望帮助菜单可以进入检查更新和关于，以便减少标题栏按钮。
24. 作为桌面用户，我希望设置底部也保留更新、关于和诊断的完整页面路径，以便现有使用习惯不被破坏。
25. 作为桌面用户，我希望选中态通过表面明度而非到处使用品牌蓝表达，以便界面更克制。
26. 作为桌面用户，我希望标题栏和播放栏的材质能真实衬托滚动内容，以便层级自然而不生硬。
27. 作为桌面用户，我希望播放键在常见窗口宽度下保持居中，以便形成稳定的肌肉记忆。
28. 作为桌面用户，我希望播放模式、音量和更多操作可用鼠标与键盘完成，以便不依赖特定输入方式。
29. 作为桌面用户，我希望播放键和卡片不使用夸张阴影、浮起和多余强调色，以便注意力留在音乐内容上。
30. 作为推荐页用户，我希望今日主打、推荐歌曲和推荐歌单处于同一内容流，以便顺畅向下浏览。
31. 作为发现页用户，我希望页面名称与侧栏一致，并能清楚切换内容分类和发现内容来源，以便理解筛选作用域。
32. 作为详情页用户，我希望专辑、歌手、歌单和热榜只有一个标题、一个返回所有者和一个主操作，以便快速理解页面。
33. 作为详情页用户，我希望 hero 与歌曲列表一起自然滚动，以便长列表不被固定头部挤压。
34. 作为桌面用户，我希望播放队列在当前页面右侧展开，以便查看和调整队列时不丢失浏览上下文。
35. 作为正在播放用户，我希望也能切换到队列和详情，以便在大播放视图里管理当前音乐。
36. 作为正在播放用户，我希望窗口最小化、最大化、关闭和设置始终可达，以便不会被困在全屏层中。
37. 作为歌词用户，我希望当前歌词明显突出、其他歌词适度弱化，以便跟唱时快速定位。
38. 作为正在播放用户，我希望环境色来自封面但不损害文字对比度，以便氛围与可读性兼得。
39. 作为设置页用户，我希望设置保持全屏并在调整时继续播放，以便配置应用不打断音乐。
40. 作为设置页用户，我希望标签与动作处于可读内容列中，以便在宽窗口下不必来回扫视整屏。
41. 作为设置页用户，我希望相关选项被组织为少量分组，以便快速定位外观、缓存、下载、音乐源和网络设置。
42. 作为桌面用户，我希望加入歌单、下载进度和确认框使用一致的 Dialog 行为，以便理解如何关闭和继续。
43. 作为键盘用户，我希望菜单和浮层具有一致的 Tab、方向键、ESC 与焦点归还，以便完整操作应用。
44. 作为暗色用户，我希望主按钮、媒体文字、菜单和 Dialog 保持正确对比度与层级，以便不会出现黑字或浮层沉底。
45. 作为浅色与暗色用户，我希望所有产品路由都经过对应主题验收，以便不会遇到只适配了一半的页面。
46. 作为不同窗口尺寸的用户，我希望 1024、1280 和 1400 宽度下布局都稳定，以便调整窗口不会压坏控件。
47. 作为辅助技术用户，我希望正文对比度、焦点可见性和可访问名称可靠，以便感知并操作所有功能。
48. 作为已有用户，我希望歌单、收藏、历史、设置和播放语义不因 UI 改造改变，以便升级后无需重新学习或恢复数据。
49. 作为维护者，我希望样式按组件和页面拥有明确边界，以便修改一个页面不会意外改变其他页面。
50. 作为维护者，我希望歌曲行、菜单和浮层只有少量明确接缝，以便行为修复可以全站复用。
51. 作为评审者，我希望原型先验证代表性页面，以便在批量迁移前发现设计问题。
52. 作为评审者，我希望真实 Electron 提供双主题截图、几何和交互证据，以便区分代码存在与实际可用。
53. 作为发布负责人，我希望功能矩阵、静态门禁和真实验收全部完成后才转 ready，以便不把半成品作为完整重构交付。

## Implementation Decisions

### 设计基准与表面

- 采用 macOS Apple Music / SwiftUI 的信息层级、平面列表、小圆角控件和克制材质；保留 Windows 自绘窗口按钮。
- 媒体歌曲列表使用 plain list；设置与表单使用 window 底和 elevated Group。浅色主题不允许用相同的 content/card 白色假装分组。
- 一级页面使用统一 PageHeader：28/700 标题、20–24px 顶距、28px 横向留白，以及一致的 lead/actions 对齐；不使用装饰性标题图标。
- 46px 行高和 30px 封面只作为原型起点，不再是不可变验收数值。歌曲标题以 13–14px、400/500 为原型起点；有效 meta 使用 12–13px secondary；tertiary 只用于序号、计数和真正次要说明。
- 普通动作按钮使用 28px 高、6px 圆角；胶囊只用于分段和少量状态标签。卡片 hover 不位移、不起大阴影。
- 每个视图最多一个主色 CTA；选中使用表面明度差。底部播放键使用中性深/浅圆钮或纯 glyph，不使用品牌蓝大阴影。
- Dialog 使用 20px 圆角；菜单/popover 使用 10–12px 圆角。二者共享 elevated/material-overlay、动效和可访问性行为，但不机械共用一个圆角。
- 拆分强调色文字、媒体文字和真正反色文字；暗色浮层不得使用低于下方卡片的内容表面，滚动条使用语义 token。

### 导航、搜索与 chrome

- 标题栏左侧为返回、前进、设置、帮助；中间为 420px 全局搜索；右侧为窗口控制。无 logo、无竖线分隔、无 Ctrl K 文本或快捷键，搜索圆角为 6px。
- 标题栏是唯一返回/前进所有者；详情页不渲染局部返回。
- 帮助菜单包含检查更新和关于；设置底部保留完整页面入口，开发者模式和诊断路径不变。功能矩阵记录双入口。
- 标题栏与播放栏允许内容从下方滚动，并提供滚动边缘。侧栏没有内容穿透时使用有意实色；若不实现滚动穿透，chrome 统一采用克制实色而非增加 blur。
- 播放栏维持三列 grid 和单一三态播放模式按钮；音量可折叠但保留静音、键盘调值与可见焦点。
- 正在播放位于全局标题栏之下，不得遮挡窗口控制。标题栏在正在播放状态提供收起和页面身份，并允许进入设置。
- 进入设置时同时移除正在播放层及其 footer，并隐藏普通播放栏；返回不得复活旧歌词层，播放不得中断。

### 页面类型与信息架构

- 推荐、发现、我喜欢的音乐、最近播放、我的歌单、本地等一级路由使用统一 PageHeader。收藏和最近播放以播放全部为主操作，清空历史为次级危险操作。
- **信息架构（2026-10-29 用户拍板，#694）**：侧栏分两段——「发现」（推荐 / 发现）与「资料库」（我喜欢的音乐 / 最近播放 / 我的歌单 / 本地）；「资料库」只作分组标题，不再是对应页面，独立聚合页退役，`/library` 重定向 `/favorites`。
- 内容库页面的 segmented 只允许 **歌曲 / 专辑 / 歌手** 三个过滤维度（同一批数据的三种看法）；本地页承担导入文件夹 / 扫描 / 空态，下载管理改为页头「已下载」次级入口，不单独占段；我的歌单保持纯网格。
- 推荐保留今日主打、推荐歌曲和推荐歌单。首屏双列必须处于同一页面流，不使用独立滚动；推荐歌曲使用 plain list，歌单使用内容网格。
- 发现页 h1 与侧栏统一为“发现”，“今天听什么”只可作为 lead。分类使用文字 tab 或 segmented；音乐源筛选使用紧凑 segmented 或下拉。
- “搜索来源”只影响全局搜索，“发现内容来源”只影响发现内容；两者不得混用状态或文案。
- 专辑、歌手、本地歌单、发现歌单和热榜统一为 hero + 歌曲列表，只保留一个 h1 和一个主 CTA。hero 与列表进入同一滚动上下文。
- 专辑和歌单封面以 180–200px、10–12px 圆角和轻阴影为原型起点；歌手允许圆形媒体变体；列表前保留 20–24px。
- 播放栏的队列入口打开当前内容右侧的非模态队列面板，保留拖拽、虚拟滚动、稳定随机序列和批量能力；旧队列路由兼容映射到面板。
- 正在播放保留左侧封面与播放控制、右侧歌词/队列/详情的双列布局；底部只保留音质、视图切换和音量，不重复整套播放控制。
- 当前歌词以 20–22px/700 为原型起点，非当前为 16–18px 并降低视觉强度；环境色先按主题约束亮度和饱和度，再调整透明度。
- 设置保持独立全屏路由并继续播放。页头与 Section 共用 720–800px 最大内容列并居中，窄窗口保留 24–28px 边距；相关设置合并为少数 Group。

### 歌曲行与播放契约

- 建立一个歌曲行密度协议，统一普通列表、分组列表、可排序行、拖拽预览、骨架和虚拟列表测量；不要把拖拽并入普通 SongList。
- 行协议包含排版、封面、操作可见性、时长和虚拟测量，但列、封面和批量能力由场景配置。
- 普通浏览不显示复选框；显式进入选择模式后才显示复选框和批量工具栏，完成或取消后退出。
- 点播契约统一为 onPlay(song, queue, index)。列表只回传当前展示队列与索引，不隐式写 playerStore；调用方统一负责设置队列和播放。
- 分组搜索也必须传递其真实展示队列，不得退化成只有单曲参数的另一套语义。
- 保留换源、收藏、下载、加入歌单、拖拽、过滤、无限滚动、空态和骨架；没有当前歌曲时禁用播放栏加入歌单。
- 专辑与发现歌单批量下载必须调用真实批量回调；没有能力的入口不得渲染为可用按钮。

### 原语、样式与交付阶段

- 延续自建 Button、IconButton、Checkbox、Segmented、Dialog、Toast 等原语；抽取共享 Menu 行为，统一首项聚焦、方向键、Home/End、ESC 和焦点归还。
- 下载进度迁入统一 Dialog，不再维护独立面板语言和独立动效。
- 先按组件和页面拆分路由全局注入的合并样式，并确认局部引用，再删除全局入口；不得直接删除样式导致页面裸露。
- 不重写移动端或 core 播放链，不改变持久化键和数据模型。
- 保留现有 worktree 有效成果；开始时冻结并行写入并保存完整 diff，禁止用 reset/clean 丢弃未跟踪原语。
- 第一阶段重写规格并制作资料库、专辑详情、推荐、发现、设置、队列面板、正在播放七个原型，验证 1024/1280 和双主题。
- 第二阶段完成样式、token、共享原语和点播契约地基；第三阶段用资料库和专辑详情做垂直切片。
- 垂直切片验收后，再按一级页面、内容详情、推荐/发现、设置/浮层、队列/正在播放推广。
- 不为容易逆转的视觉细节新增 ADR；既有原语、全屏设置和选中色 ADR 保持不变。

## Testing Decisions

### 好的测试与接缝

- 只断言用户可观察的外部行为：可访问名称、可见文本、实际回调、焦点顺序、键盘操作、计算可见性、几何位置和运行时状态；不把组件内部结构或 CSS 源码字符串当作完成证据。
- 组件接缝使用现有 renderer RTL 与 electronAPI stub，覆盖原语、歌曲行、页面入口和状态转换。
- App 状态测试不得同时替换标题栏和正在播放这两个参与交互的组件；覆盖导航复位及 ViewTransition 分支，但不让 jsdom 承担布局证明。
- 最高验收接缝是真实 Electron：负责遮挡命中、计算可见性、窗口控制、双主题、滚动材质、几何和跨页面交互。Chromium+stub 只作快速辅助，不得标成真实 Electron 证据。
- 原型评审是独立设计接缝：七个代表页面在批量实施前先通过 1024/1280 和深浅主题检查。

### 模块与行为覆盖

- 原语：按钮、分段、Checkbox、Menu、Dialog、Toast 的默认、禁用、键盘、焦点和关闭行为。
- 歌曲行协议：普通、分组、可排序、拖拽预览、骨架与虚拟测量一致；场景列正确；选择模式进出正确。
- 播放契约：断言调用方收到歌曲、展示队列和索引，列表不隐式写 playerStore；分组与拖拽场景同样覆盖。
- 页面行为：内容库三视角（歌曲/专辑/歌手）切换、本地页导入/扫描/空态、收藏文案、历史播放全部、两个批量下载真实调用、无当前歌时加入歌单不可用。
- Chrome：1024/1280/1400 使用运行时几何检查播放键中心；检查搜索来源首末项命中与实际选择，验证 Ctrl K 无行为。
- 可访问性：帮助、更多、来源、正在播放菜单检查 Tab、Enter、方向键、Home/End、ESC 和焦点归还；音量检查展开、键盘调值和焦点可见。
- 材质：读取计算背景和 backdrop-filter，并验证滚动穿透或实色回退，不只检查 token 存在。
- 正在播放 → 设置：覆盖动画中与动画后、ESC 与导航交错；分别断言正在播放层/footer 消失、普通播放栏计算隐藏、设置标题出现、返回不复活旧层、播放不中断。
- 全量视觉：全部产品路由和设置子页执行浅色/暗色真实 Electron 截图与页面错误检查；发现必须真实提交搜索并覆盖单源与全部源。
- 静态门禁：typecheck、lint、design-lint strict 和相关 Vitest；最终按仓库 verify 流程执行需要范围的验证。

### 既有先例

- 复用 renderer RTL 页面测试和 electronAPI stub 作为组件与页面接缝。
- 复用现有 UI 截图脚本作为 Chromium 辅助证据，但新增主题循环、真实搜索和页面覆盖，且不改写证据等级。
- 按 runtime-verification skill 记录真实宿主进程、断言、pageerror 与截图；截图作为 PR 证据，不入库。

## Out of Scope

- 移动端布局、Expo 模块和移动端主题改动。
- core 播放解析、稳定随机序列算法、跳歌护栏和换源算法改动。
- 歌单、收藏、历史、设置等持久化模型或键的迁移。
- macOS 原生交通灯、窗口原生 vibrancy 或 Mica 接入。
- 国际化、安装包签名、更新通道与发布流水线。
- 新增音乐内容能力或与 UI 收口无关的功能。
- 为统一而新增的 t-* 排版工具体系、独立图标尺寸 token 和 design-lint 表达式扩展；可在相关改动中顺手完成，但不作为视觉完成标准。
- 为容易逆转的视觉细节新增 ADR。

## Further Notes

- 本规格取代同日早稿；早稿的 15/600 标题、11px tertiary 有效 meta、常驻复选框、全部页面同一 SongList、Hotlist/DiscoverPlaylist 标准页头和浮层/暗色 P1 划分均不得继续作为实施依据。
- 既有“自建 UI 原语、设置全屏视图与选中不用品牌蓝”ADR 继续有效。
- 原型只用于确认设计，不作为生产代码直接合入；长期文档不引用一次性验收截图。
- 功能矩阵必须分别记录 Chromium+stub 和真实 Electron 证据，旧截图不能自动继承为新 UI 通过状态。
- PR #691 只有在全量范围、功能矩阵和真实验收全部闭环后才可转 ready。

## 原型评审结论（#695）

- 矩阵：资料库 / 专辑详情 / 推荐 / 发现 / 设置 / 右侧队列面板 / 正在播放 × 1024/1280 × 浅色/暗色 = 28 张；生成与断言脚本 `prototypes/shots.mjs`（原语样张页不计入矩阵）。
- 页面头：标题 28px/700、行高 1.2；页面上 24px、左右 28px；头部底距 18px；lead 13px tertiary、与标题列距 12px；操作区右对齐、间距 8px。
- 歌曲行：46px 高、14px 横向内边距、10px 列距、30px 封面/4px 圆角；标题 14px/500；歌手与专辑 13px/400 secondary；序号/时长 13px tertiary；行操作 hover 才显示。
- 按钮：普通 28px 高/6px 圆角/12px 横内边距/13px 500；小号 24px；图标 28×28；每视图最多一个主色 CTA；分段 28px 高、段 24px、胶囊。
- 圆角：行与封面 4px；按钮/搜索框/菜单项 6px；卡片/菜单/Toast 10px；Group/Hero 封面 12px；Dialog 20px。
- 材质：标题栏 44px、播放栏 68px；浅色 rgba(255,255,255,.72)、暗色 rgba(22,22,24,.72) + blur(24px) saturate(180%)；必须真实滚动穿透，否则回退克制实色（D4）；侧栏实色无 blur。
- 队列面板：宽 320px，右贴边，top 44px / bottom 68px；头部 48px、行 46px、底部 44px；卡片表面 + 左 hairline；非模态，1024 下覆盖内容而不推挤。
- 设置内容列：全屏路由，隐藏侧栏与播放栏；内容列 max-width 760px，1024 实测 740px、1280 实测 760px；左右边距 28px；导航 200px + 28px 间距。
- 正在播放：标题栏之下、隐藏侧栏；左列 clamp(380px, 40%, 460px)（1024→384、1280→460），右列 flex（1024→528、1280→708），列距 48px；封面 300px/12px 圆角；footer 56px；当前歌词 20px/700、非当前 17px/400 tertiary。
- 环境色：浅色 hsla(238,42%,62%,.18)、暗色 hsla(238,42%,26%,.55)，radial-gradient(120% 85% at 12% -12%) 铺底；取封面 hue，按主题限亮度/饱和与透明度，保文字对比。

### 与规格冲突处的裁决

- **队列面板几何（2026-10-29）**：L203 的「320px 右贴边、top 44 / bottom 68」作废——用户在 #707 验收时明确要求「直接搞一个弹出层，不要侧边栏，再点一次图标收回」，实现按浮层（宽 460、右 12、距播放栏 2、圆角 10）执行，本规格以该条为准。
- **卡片封面圆角**：L201「行与封面 4px」适用于所有封面图（含内容卡媒体）；「卡片 10px」指有实体表面的卡片容器（Group / 菜单 / Toast），内容卡本身无容器表面，媒体按 4px 执行。
- **内容网格**：`--content-grid-min: 156px`，列距 `--space-4`(16)、行距 `--space-5`(20)；1024 四列、1280 五列、1400 六列（175px）。三处网格（.card-grid / .artists__grid / .rec-playlists）共用同一组 token，不得各写断点。


- 46px 行高与 30px 封面按原型基线保留，但按 L94 不作为不可变验收值，允许 ±2px 的密度微调，验收看排版与对齐。
- “正在播放位于全局标题栏之下”：裁决为隐藏侧栏、占满标题栏以下整幅宽度；标题栏继续拥有返回与窗口控制（L107）。
- 队列面板“非模态”：1024 下裁决为覆盖内容（宽 320px 固定），不压缩列表宽度；1280 按同一宽度覆盖，不做推挤动画。
- 材质按 D4 顺序：先实现真实滚动穿透，blur 只作增强；若某平台不能穿透，标题栏/播放栏统一使用克制实色。

### 未决项

- 标题栏在正在播放态的收起按钮与页面身份文案未在原型出现，按 L107 在 #706/#710 实现。
- 队列面板拖拽排序、批量操作与虚拟滚动的交互态需在 #707 用真实 Electron 验证。
- 1400 宽度与真实 Electron 双主题全路由证据不在本票矩阵内，由 #694 收口阶段覆盖（用户故事 46）。
